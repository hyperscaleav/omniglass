# sim: the Omniglass device simulator

The simulator serves a fleet of fictional AV and IT devices, each on its own loopback address,
speaking the protocols real gear speaks (HTTP and HTTPS, SNMP, SSH, Telnet, raw TCP line
protocols, UDP, WebSocket, server-sent events, signed webhooks) from one live state per device.
An outpost collects from a simulated device exactly as it would from hardware. It is the test
bed for the end-to-end tests, the screenshot harness and the lab, and a teaching surface: an
operator can break a device on purpose and watch the monitoring loop respond.

It is part of the single Omniglass Go module and binary, not a separate program.

## Layout

| Path | What it is |
| --- | --- |
| `sim/` | The engine: devices, faces per protocol, behavior, faults, state, observation. |
| `sim/profiles/` | Device profiles as data (`devices/`, `surfaces/`, `templates/`), embedded into the binary. |
| `sim/surface/` | Protocol surfaces a Go device family declares in Go (`nvp`, `snmp`, `httpapi`), byte for byte what the YAML surfaces and repeated profile pieces answer. |
| `sim/behave/` | The shared, typed behavior primitives a family composes. |
| `sim/profile/` | The profile model: parse, validate, resolve includes. |
| `sim/spec/` | What defines a device either way: the `Definition` every consumer reads, the Go family `Spec`, and the `Catalog` that resolves a product. |
| `sim/device/` | Go device families, one package per wire API; the list is generated by `make gen`. `internal/bind` joins the behavior primitives to a family's state. |
| `sim/fleet/` | Deterministic naming and enrichment of fleet members. |
| `sim/impair/` | Network impairment (firewall table and qdisc) for a simulated device. |
| `sim/simfleet/` | Fleet and system plans built from profiles. |
| `sim/simhub/` | Registry of the simulators connected to a server. |
| `sim/simoutpost/` | The simulator running beside or inside an outpost. |
| `sim/mailsim/` | The simulated mail server. |
| `sim/simtest/` | Test helpers for loopback addressing. |

## Running it

- `omniglass sim run` runs beside an outpost with that outpost's credential (the same
  `OMNIGLASS_SERVER`, `OMNIGLASS_OUTPOST_NAME` and `OMNIGLASS_OUTPOST_TOKEN` as `outpost run`),
  pulls the devices placed on that outpost and serves them. `omniglass sim mail` runs the
  simulated mail server.
- `make lab` brings up a server, an outpost and a simulated fleet together;
  `make test-lab LAB_RUN=<test>` runs one lab scenario test.
- `make bench-sim` serves a 1,000-device fleet and reports startup time.

## Writing a device profile

A profile is one YAML file in `sim/profiles/devices/`, named for the product it simulates. It
declares the product's identity (`name`, `manufacturer`, `model`, `device_type`), its interfaces
and protocol surfaces, its state, and the behavior that moves that state. Surface pieces two
profiles share live in `sim/profiles/surfaces/` and are taken in with `include:`. The editor
schema is `sim/profiles/devices/schema.json`; the first line of a profile points at it. Start
from the closest existing profile and copy its shape. Coverage of seeded products by profiles is
accounted for in `sim/profiles/coverage.yaml` and checked by the tests.

## Writing a Go device family

A family is a package `sim/device/<family>` that exports `func Spec() spec.Spec`: one wire API,
implemented once, its models the rows of a typed table. `make gen` registers the package; a product
resolves to a family when one claims it, else to its YAML profile. The worked example is
`sim/device/borealedge`, the Boreal Edge display, with `borealbeam` and `borealcast` beside it.

1. **Record the profile first**, when one exists. On the base branch, play the family's script against
   the YAML profile and commit the transcript as testdata (`sim/testdata/wire`, `sim/wire_golden_test.go`
   and `sim/boreal_wire_test.go` are the harness and a script). Then write the family and make
   `sim/boreal_parity_test.go`'s pattern pass: same status, headers, bytes, state, SNMP types and
   values, drift sequences and room-day behavior. Delete the profile and its templates in the same slice.
2. **The model table.** A typed `Row` (`Product`, `Diagonal`, `Resolution`, and whatever else the
   models differ by) written once, wrapped with `spec.Table`, each row's `Model`, `Summary` and `State`
   overlay saying what the product reports of itself. Five sizes are five rows, never five packages;
   a model gets a package only when its API differs.
3. **Interfaces and state.** Declare the surfaces as `profile.Interface` (protocol, port, auth) and the
   state tree with its defaults. A read-derived value (uptime) is a `Computed` field.
4. **Answers.** JSON is a typed struct through `httpapi.Document` (or `httpapi.Status`). A route that
   sets state from a body is an `httpapi.Control`, a reboot an `httpapi.Action`; SNMP is
   `sim/surface/snmp` plus typed scalars (`surface.Text`, `surface.Integer`, each `.At(statePath)`);
   a line protocol is `sim/surface/nvp`. A device web page is `html/template` over a typed view struct,
   both in the package (`//go:embed`). Read state with `spec.String`, `Int64`, `Float` and `Bool`.
5. **Behavior.** `spec.Tick`s built from `sim/device/internal/bind`, which joins a `sim/behave`
   primitive to the family's state paths; the paths a tick writes are declared in `Writes`. Write a
   behavior inline only where no primitive owns it, and add the primitive to `sim/behave` first when a
   second family will want it.
6. **Tests.** `spectest.Conform(t, Spec())` over the whole table, then the family's own: a
   `spectest.NewFake` stands in for the device, so a handler, a surface and a tick are unit tests with
   no engine. The engine-level proof is the parity test above.

`sim/spec/spectest` is also a small family used by the engine's tests.
