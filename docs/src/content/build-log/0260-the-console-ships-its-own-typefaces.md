- **The console ships its own typefaces.** `index.html` linked `fonts.googleapis.com` with
  `display=swap`, so the console painted in fallback metrics until a third party answered: wrong on
  the closed campus and AV networks this product is deployed into, and the cause of main going red
  at `3b16b325`. The docs capture opens a new browser context per shot, so every shot re-raced the
  CDN; two of ten lost, were written anyway, and failed the zero-tolerance freshness gate as UI
  drift on a PR that changed no UI (the two differed in the same 3,806 and 456 sidebar pixels, and
  in 20,955 greyscale glyph edges against 1,405 colourful, which is text metrics, not content).
  Both families are OFL 1.1 and are now vendored under `web/public/fonts/` (54 files, 1,005,028
  bytes, both `OFL.txt` beside them), copied verbatim into the Vite output the binary embeds and
  served by it as `font/woff2`, which the handler states itself because the runtime images carry no
  mime database. Every script the CDN served is vendored, not a latin subset, so no
  operator-supplied string renders differently than before; `unicode-range` keeps the split so a
  latin page still fetches one file. `font-display: block` replaces `swap`. `web/src/fonts.css` is
  generated by `web/scripts/vendor-fonts.mjs`, never hand-edited. The capture now refuses to
  photograph a fallback render (`web/e2e/fontguard.mjs`: every face declared, both families rendered
  from their own files, no font request failed), which is the half that let a wrong PNG ship
  silently; `DOCS_SHOTS_PROXY` retires with the dependency it worked around. The ten shots recapture
  byte-identical, which is the proof the vendored files are the same faces the browser was fetching
  (ADR-0121, #775).
