title: "A telemetry batch reads and locks once, and stamps seen inside its transaction"

summary: "The batch's transaction carries the event rules it read, the owners it marked for a calc rule and the property series it locked, so no lane reads, probes or locks them a second time; the endpoints a batch carried are stamped seen inside its transaction rather than in a second commit after it (amends ADR-0311 point 2); the ingest consumer reads the catalogs' fingerprint at most once every five seconds rather than per batch (amends ADR-1279, whose catalog change was honored by the next batch); a calc mark that is already pending writes no tuple. A node batch drops from 19 to 13 statements"

- **Date:** 2026-11-14 | **Status:** Accepted | **Pages:** [storage](/architecture/storage/), [metrics and properties](/architecture/properties/)
- **Decision:** (#1928.)
  1. **The transaction carries what it took.** `batchTx` records the event rules `lockGroups` read FOR SHARE, the owners it marked for each calc rule and the property series whose advisory lock it took. The rule evaluator, the calc marker and the property lane ask it first, so a lane does not read the rules, probe the calc marks or lock a series the batch already holds. The record is filled only by `lockGroups` on the outer transaction, shared by its savepoints, and starts empty on each retry, so the lock order (rule rows, then calc marks, then the series in sorted order) is unchanged.
  2. **The seen stamp is in the batch's transaction.** `LandBatch` stamps the endpoints its admitted groups carried (and the batch's own `SeenEndpoint`) as its last write (a redelivery that lands nothing still stamps), under the same `liveStampEvery` rate limit and `SKIP LOCKED`, so a batch commits once. A refused group's endpoint is not stamped. This reverses ADR-0311 point 2's "the freshness stamp stays after the transaction": the stamp now holds an `endpoint_live` row lock until commit, which `SKIP LOCKED` keeps from blocking a concurrent stamp, and a failed stamp retries or fails the batch with the rest of it.
  3. **The fingerprint is read at most every five seconds.** The registry cache keeps the time it last read a matching fingerprint and reuses the registry without a read inside `fingerprintEvery` (5 s). A catalog change (a type, a calc rule, a command type) is honored by the first batch after that interval, not the next batch, as ADR-1279 and ADR-1299 had it.
  4. **A repeated calc mark writes no tuple.** `markCalcPending` keeps `on conflict do update`, because the update's row lock is what holds the mark against a calc evaluation until the batch commits, and guards it with `where false`: Postgres locks the conflicting row before it judges the guard, so the lock holds and no new row version is written. `do nothing` takes no lock and is not used.
- **Context:** `TestIngestFootprint` counted 19 statements for one node batch: the rule rows and calc marks read again by the lanes after `lockGroups` had taken them, a series lock taken again by the property lane, the fingerprint read on every batch, and the seen stamp as a second transaction of its own (a begin and a commit). Measured after: a node batch 13 statements, a collection report batch 10 (from 13), and `LandBatch` over a judged workload 80 (from 84) and steady 15 (from 19, `TestLandBatchTakesEachLockAndRuleReadOnce`). The issue's spec named an `is distinct from` guard for the calc mark; the update sets `marked_at` to itself, so the guard is always false and is written as `where false`.
- **Not chosen:**
  - **`on conflict do nothing` for the calc mark.** It writes no tuple, but it takes no row lock either, so a calc evaluation could clear the mark under an uncommitted batch (`TestCalcMarkHeldByUncommittedBatch` fails with it).
  - **Keeping the stamp after the commit.** It costs a begin and a commit per batch, and a batch whose stamp failed had already landed, so a seen endpoint could read stale with its samples stored.
  - **Reading the fingerprint per batch.** One read per batch per node is the largest fixed term left once the lanes stop repeating; at a node's one-second flush window a fleet of a few hundred nodes read it hundreds of times a second for a catalog an operator edits by hand.
