title: "A batch lands its metric lane in one statement, except a series it carries twice"

summary: "An ingest batch resolves each owner and reads the transaction's clock once for every lane (a batchTx wrapping the batch's transaction, which ownerArcValue and dbNow answer from), and lands every metric sample whose series it carries once in one ordered statement; a series it carries more than once keeps the per-sample insert-then-judge order, so rule evaluation sees exactly what it saw before. A node batch drops from 29 to 19 statements"

- **Date:** 2026-10-28 | **Status:** Accepted | **Pages:** [samples](/architecture/properties/)
- **Decision:** (#1274.)
  1. **One resolution and one clock per batch.** `LandBatch` wraps each attempt's transaction in a `batchTx`. `ownerArcValue` answers an owner's primary key from it after the first lookup, and `dbNow` answers the transaction's `now()` from it after the first read. Every lane and the lock pass share both. The answers are the ones the database would give: `now()` is the transaction's start time, the same for every statement in it, and an owner's key does not change inside the batch's transaction. A deadlock retry opens a fresh `batchTx`, so nothing carries across attempts.
  2. **The metric lane lands in one statement.** Every sample whose series (owner, key, instance) the batch carries once goes into one `insert ... select ... from unnest(...) with ordinality ... order by ord`, so those rows take ids in the order the batch carried them. A series carried more than once lands after them, so across series ids no longer follow the batch's order. Nothing reads them that way: within a series (ADR-0061's order) the order holds, and no reader orders by id across series. The type joins by name with a left join, so an unknown name fails the insert on `metric_type_id`'s `NOT NULL`, as the per-sample subselect did, rather than dropping the row.
  3. **A series carried more than once keeps the per-sample path.** The rule evaluator's newest-row check asks whether a later sample of the series already exists. If a batch's later sample of a series were in the table before its earlier sample was judged, the earlier one would be skipped as stale. So those samples are still inserted and judged one at a time, in order. Rules are judged for every observation, in the batch's order, in both paths. `TestABatchJudgesEachSampleOfASeriesInOrder` holds this: one batch carrying 31 then 20 for a fire-over-30, clear-under-25 rule fires and clears. Batching every row fails it, deriving nothing.
  4. **The insert stays inside the admitted write path.** It is a closure in `writeMetricSamples`, after `admitWrites`, so `TestEverySampleWritePathAdmitsItsWriter`'s invariant (every function that writes a sample row admits its writer) holds as designed.
- **Context:** The ingest footprint (ADR-1272), after #1279, put 29 statements on a node batch of five observations. Six were the same scoped component read (one per sample, plus the lock pass), three were `select now()` (one per lane evaluator and clock), and four were one `INSERT` per metric. Measured after (`TestIngestFootprint`; `BenchmarkIngestFootprint`, back to back against #1279's branch on one host): **19 statements per batch**, about 2.3 to 2.6 ms instead of 3.4 to 4.0 ms, 596 allocations instead of 811, about 47 to 57 KB allocated instead of 67 to 80 KB. Rows, heap density and index size are unchanged.
- **Not chosen:**
  - **Batching every row and judging afterwards.** Changes rule outcomes for a series repeated in one batch (the test above).
  - **`COPY` into the metric table.** The fastest path for bulk loads, but a COPY cannot join the type by name, return a NOT NULL failure as the per-sample path does, or share the transaction's statement shape with the rest of the batch. At a few rows per batch, one `insert ... select` is the same round trip.
  - **Batching the property lane.** Properties are transition-only: each row's insert is conditional on the series' latest value under a per-series lock. They are sparse by construction, so the gain is small and the risk is not.
