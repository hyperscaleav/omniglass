- **Date:** 2026-10-28 | **Status:** Accepted | **Pages:** [collection](/architecture/collection/#collection-telemetry-every-endpoints-account-of-itself), [settings](/architecture/settings/), [admin guide](/guides/admin/)
- **Decision:** (#1369, ruled 2026-10-28 on #1266 and #1369.)
  1. **Built-in and collected data.** Collected data is what a driver reads from the device's API, declared by its polls and listeners. Built-in data is what Omniglass knows about the endpoint itself: every endpoint gets it, whatever its driver, because the endpoint cannot work without it, and a driver never declares or emits it (it only tunes how some is gathered, its ladder). Beside the probe samples and a session's state, every endpoint's built-in data now includes its own collection, so a device that only pushes, or reports nothing of its own, still carries telemetry.
  2. **Aggregated where it is counted, once a window.** The node counts each endpoint's poll runs, scheduled or run now (how long, and which failed: faulted and landed nothing, as the poll scheduler reads a failure), each due poll its gate refused (a failure with no time, so the mean stays the time of the polls that ran), and its held session's or udp socket's messages (claimed by a listener, or not; a session or socket recycled mid-window hands its counts to the next report). The server's webhook receiver counts each endpoint's accepted and refused posts. Each reports once a **report window**, so the cost is a few rows per endpoint per window however fast a driver polls or a device pushes. Measured: one report batch is 13 statements and two rows for an endpoint that both polls and listens (`TestCollectionReportFootprint`, exact); across the learner lab's mix, about 7% more metric rows.
  3. **Dense where silence means something, sparse for errors.** `poll-duration` lands every window a poll ran, and `push-message-count` every window the endpoint is held, zero included, so a quiet device reads quiet rather than missing. `poll-failure-count`, `push-unclaimed-count` and `webhook-refusal-count` land only when nonzero. `webhook-post-count` lands when nonzero and then one zero after a window with posts, so the series shows a stream stopping; after that a quiet webhook endpoint lands nothing, and its last heard says how long. The server does not land a zero for every quiet webhook endpoint every window: it would need to read every one, and each server of an install would land its own.
  4. **One writer class per key (ADR-0161).** The four node keys are `node-probe` and node-only (`probekeys`), so the push lane refuses them, as it does every probe key. The two webhook keys are `platform`: only the process counts its posts, so a node and a push are refused them, and the receiver writes them through the gateway's process writer, in the metric write path, so an event or calc rule reads them as it reads any metric.
  5. **The endpoint is the series.** A row's instance is its endpoint's name, as every node-observed row's is, so an endpoint's several polls share one `poll-duration` series. A node publishes an endpoint's rows under the least of its task ids in the worklist it holds when the window closes, never one remembered from the window's start: a driver revision mid-window replaces the ids, and a row under a deleted one would be dropped as an orphan and raise the node's stuck-task signal. An endpoint no longer in the worklist reports nothing. The server lands each component's webhook counts in a transaction of its own, so a component deleted since its last post drops only its own rows (the review's blocker; anti-pattern `deleted-owner-sinks-the-batch`).
  6. **The window is a platform setting for now.** `collection.report_seconds` (platform domain, client-visible, 60 by default, 10 to 3,600) rides the worklist to every node on each pull and is read by the receiver when it arms a report. A node's `Config.ReportEvery` and the API's `WithCollectionReportEvery` override it for tests. This is the interim of the cadence model ruled on #1373: each endpoint type's catalog entry holds its built-in keys' defaults, a driver overrides them per endpoint type, and an operator overrides them down the cascade.
- **Context:** #1266 set the lab's bar at telemetry on every component and every system. The inventory found a webhook-fed component carried nothing of its own (a post stamped last heard, and refusals were a counter on the token row), a pushed line no listener claimed reached only the node's log, and a poll's time and failures were not measured at all; a failing poll landed one `collection-failed` per change of fault.
- **Not chosen:**
  - **A row per poll run or per message**, as the probe timings are. Finer, but about 19% more lab rows today, growing with poll rate and message volume.
  - **Every key every window, zeros included.** Simpler to chart, about twice the rows of the sparse rule for the error counts.
  - **One key written by both the node and the server** (a `push-message-count` for webhooks too). A key has one writer class, and the server's count and the node's are different observers.
  - **A window per endpoint type now.** That is #1373's model; one window first keeps this slice to the telemetry itself.
