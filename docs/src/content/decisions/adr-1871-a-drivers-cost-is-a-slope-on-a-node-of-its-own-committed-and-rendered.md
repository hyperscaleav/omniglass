- **Date:** 2026-11-13 | **Status:** Accepted | **Pages:** [scaling](/architecture/scaling/#what-a-driver-costs-a-node), [nodes](/architecture/nodes/#self-monitoring-the-node-reports-itself)
- **Decision:** (#1871.) `omniglass lab perf drivers` brings up a lab with no fleet and measures each shipped driver on a node container of its own, its simulator in a second container sharing the node's network namespace, so the node polls on its own loopback and the simulator's work lands in a different cgroup. The node runs the product's default cadence, not the lab's quicker one, so its background work is a deployed node's. Each driver is read at 0, N, 2N and 3N components (N bringing about `--step-tasks` tasks), each step over a window at least as long as the driver's slowest poll. CPU per task is the least-squares slope over every step. Memory per task is the slope over the three loaded steps alone, because a node's working set jumps when a driver's first tasks land (its lanes and heap warm) and only then rises by a slope; the loaded line's value at zero tasks, over the idle node, is the warm memory, a one-off cost. A step off its line by more than 10% of the rise in memory, or 25% in CPU, refuses that figure, listed as not measured with why; the other figure stands, and only a driver with neither is left out of the measured rows. A driver whose memory does not fit is swept again on a fresh node at four times the step, up to `--max-step-tasks` (6400 by default), and the attempt with the most figures is kept, the bigger step on a tie; each row records its step. A loaded line that starts below the idle node leaves the warm figure empty with that reason, never zero. CPU per run (the slope over the run rate) is cross-checked by the node's mean `poll-cpu-time`, reported as the thread share. The run writes `internal/labfootprint/drivercost/shipped.json`, stamped with its date and build, and with its host's fingerprint when the lab's Docker daemon is local; `make gen` joins it with the plan (every shipped driver, and every driver no shipped product uses or that declares no polls, with that reason) and renders the table on the scaling page.
- **Consequences:** The table is a committed measurement, not a generated fact: a driver added after the last sweep shows on the page as not yet measured until a sweep is committed, so the page never omits a driver nor shows a figure no run produced. The figures hold for one host class and for simulated devices, so the page reads them as relative cost and order of magnitude. A full sweep takes hours (the five-minute polls set most drivers' windows), so it is run by hand on a test VM, like the perf gate (ADR-1787).
- **Context:** The issue placed the table on "the sizing docs page" and listed task kind and interval as columns. There is no sizing page; the scaling page is where a node's size is read, so the table lands there. Every swept task is a driver poll, so the kind column would be constant; the driver's poll intervals stand in for the interval. A driver "without a simulator" is, in the shipped plan, a driver no shipped product is on: the simulator serves products, so those are listed as not measured with that reason.
- **Not chosen:**
  - **Running the sweep under `make gen`.** It needs Docker and hours; `make gen` must stay fast and offline.
  - **Two steps.** Two points always fit a line exactly and could never show a bend, so each fit needs three.
  - **One memory line through the idle step.** An SNMP driver read 15.8, 25.9 and 27.4 MiB at 0, 400 and 800 tasks: a warm-up jump, then a slope. One line through all three refused the driver, and a looser bound would have read the jump as a per-task cost several times too high.
  - **One step for every driver.** The first full sweep, at 400 tasks a step, fit CPU on all 20 shipped drivers and memory on 7: a driver costing about 5 KiB a task rises about 4 MiB across its loaded steps, while one SNMP driver's loaded steps read 30.9, 28.8 and 28.7 MiB: the heap's own swing is as big as the signal. A step big enough for the cheapest driver at the start would make every driver's sweep slower; escalating only the misses keeps the cheap case cheap.
  - **A looser memory bound.** It would pass the misses by writing the heap's swing down as a per-task cost.
  - **Refusing the whole driver when one figure fails.** Memory and CPU are measured on the same steps but bend for different reasons; a driver whose CPU is a clean line keeps that figure when its memory does not fit.
  - **The scale lab's nodes.** They run the simulator in process (`node run --simulate`), so their cgroups hold the devices' cost as well as the node's.
