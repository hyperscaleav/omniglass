A **lab** is a working omniglass on your own machine, brought up by one command, to learn on. It
runs the real server and console, its own Postgres, and an edge node that runs the simulator in its
own process, serving a fleet of simulated components and collecting from them for real. Break a
component on purpose and watch the platform notice. The only thing it needs is Docker, on Linux,
macOS or Windows.

## Three commands

From a checkout:

```bash
git clone https://github.com/hyperscaleav/omniglass.git && cd omniglass
make
./bin/omniglass lab run
```

`make` builds two things from one Dockerfile, with nothing but Docker: the image `omniglass:dev` and
this machine's own binary, `bin/omniglass`, both stamped with one build id. It builds and runs
nothing else. `make lab` is the short form of the last two commands (`make`, then
`./bin/omniglass lab run`; `LAB_ARGS` passes flags, as in `make lab LAB_ARGS=--fresh`).

With a [release binary](/guides/install/#download-a-binary) there is nothing to build: run
`omniglass lab run`, and it pulls its own release's image.

## What you see

The lab says what it is doing while it comes up, one line per stage, then where to go:

```text
  image      omniglass:dev (built by make beside this binary)
  network    omniglass-lab_default (a private bridge; only the console is published)
  database   Postgres is ready
  seed       the dev fleet, seeded on this lab's first run
  server     answering at http://127.0.0.1:8080/web
  sign in    the login dev / dev works
  node       edge-hq with its simulator: 124 of 124 simulated components running
  collecting 128 of 128 simulated endpoints up, and 3 broken on purpose for you to find

Your omniglass lab is ready (it took 14s).

  Console    http://127.0.0.1:8080/web
  Sign in    user dev, password dev

  Stop it    press Ctrl-C here. Your lab's data is kept for next time;
             omniglass lab run --fresh starts over from the seed.

Where to go next: the guided walkthroughs, each recorded on this same lab,
so every screen matches yours:
  https://docs.omniglass.hyperscaleav.com/guides/lab/#walk-through-it

The lab is one Docker project; see it with: docker compose -p omniglass-lab ps
```

Ready means four things, each checked before the lab says so: the console answers at the printed
address, the printed login signs in, the simulator reports every simulated component `running`, and
every simulated endpoint reads up except the ones the seed breaks on purpose. Two kinds of endpoint
are left out of that count: an endpoint that receives pushes (a webhook carries no reachability
verdict to wait for), and the planted faults below, which the seed marks itself rather than a list
kept here. The lab is one compose project, so `docker compose ls`, `docker compose -p omniglass-lab
ps` and `docker compose -p omniglass-lab logs server` all see it, and Docker Desktop groups it.

## Sign in

Open the printed console address and sign in as user `dev`, password `dev`: an owner, so every
screen is open to you. The login is the same well-known one every walkthrough is recorded with, so
the steps you follow match the screen you have. Every screen, the sign-in page included, carries a
**Lab instance** banner, so a lab is never mistaken for a real deployment.

The fleet is the dev fleet, the same one every walkthrough is recorded on: places with systems in
them, components of several products from several vendors, and the edge node `edge-hq` collecting
from all of them.

Every way omniglass collects runs here, healthy on at least one component, so you can watch each
one work (and a regression in any of them shows in a lab, not only in a unit test). The HQ boardroom
holds the ones the rest of the fleet does not use: the video bar's control socket over a secure
websocket, the display's web admin behind an http digest login, the touch panel's https API behind
its sign-in form, the same panel's console over ssh and over telnet (the healthy twins of two of the
faults below), and a plain ping. Beside them:

- **Webhooks arrive from the start.** The simulated meeting service is subscribed to its webhook
  endpoint when the lab comes up, as its admin would subscribe it, and posts a meeting every minute,
  so the endpoint's page reads last heard within the first two minutes.
- **An integration pushes.** A simulated booking service pushes the HQ boardroom system's bookings
  (`booking-count`, `booking-state`) through `POST /telemetry:push`, with a token the lab mints on
  every run for a service account that may push to that one system and do nothing else. Open the
  boardroom's system page to see them; a push carries no endpoint, so there is no reachability to
  read, only the values.

[Simulation](/architecture/simulation/#the-dev-fleet) lists every method and where it runs.

## Faults planted for you to find

The seed breaks a few things on purpose, so there is something real to diagnose the moment the lab
is up: the readiness line counts them as "broken on purpose". Each is marked as a planted fault in
the dev fleet's own fixtures, with a sentence saying what went wrong, and the lab reads them from
there, so the count never drifts from the seed. They are the kind of thing that happens in the field:
a credential rotated under an endpoint, a component reimaged so its key no longer matches the pin, an
agent that refuses what the endpoint presents. The walkthroughs that fix a rejected session, trust a
changed host key and fix a refused probe each start from one; try finding them on your own first.

Breaking a component yourself works too, from its page or the CLI
([break it on purpose](/guides/operator/simulation/#break-it-on-purpose)):

```bash
./bin/omniglass component impairment set <component> --unplugged   # dark on every protocol
./bin/omniglass component impairment set <component>                # plug it back in
```

## Checking that the lab is whole

The lab is also how the platform proves its own outcome: after the warm-up, every component carries
what the platform can know about it, and every system carries a value of its own. `make test-lab`
holds the lab to that, tier by tier, and a gap fails naming the owner and the tier:

| Tier | Holds for | What must be there |
| --- | --- | --- |
| **built-in** | every component, endpoint by endpoint | the data the node and the platform write about an endpoint whatever its device: reachability and its rung, a response time once the device answers, a poll duration, a held session's state and the push count of its listeners (`node-probe`), and a webhook's post count (`platform`) |
| **collected** | every component | at least one value from the device's own API that is a class signal (a power state, a mute, a scene), beyond its identity (model, serial, firmware) and `uptime` |
| **system** | every system | at least one value of its own, collected or calculated |

The built-in set is not written down anywhere to drift: the transport registry declares what an
endpoint of each transport writes, the driver's polls, listeners and session decide the rest, and
`probekeys` and the writer classes rule who may write each key. A component whose profile or endpoint
is removed fails the collected or the built-in tier by name; a component that reports only built-in
data, or only identity and `uptime`, fails the collected tier. A device that is down still owes its
reachability rung but no response time, and a telnet endpoint whose held session is up owes none
either: the probe stands down for the session, so a second dial cannot be refused by gear that admits
one client. The endpoints the seed breaks on purpose (a rotated password, a changed host key) are read
from the seed and owe no built-in key, since their ladder stops where the fault does; they must still
exist. A finding names the component with its product and location, because a component's name is
unique only within its room.

What the lab does not carry yet is listed per tier in the dev fleet's gap ledger, each entry with the
issue that closes it. The ledger is empty when the fleet is whole, and an entry fails the test as
stale the moment every owner it covers carries the tier, so a closed issue cannot leave a line behind.
`make test` does not run any of this: the warm-up needs Docker and minutes, so the check runs in
`make test-lab`, which CI may run on lab-touching changes only. The check is a function of a base URL and a client, so
the scale lab runs the same judgment against a lab of any size.

The lab can also be watched whole while it runs. With its simulator connected,
[Platform health](/guides/operator/platform-health/#with-a-simulator) closes the loop over a window
that slides every 10 seconds: every hop a request or a batch travels, from the node to the simulated
device and back to the server, read as a loss ratio. A lab that is whole reads 0 on every gap, and every
polled protocol draws its requests.

## Stopping it, and your data

Press **Ctrl-C** in the lab's terminal (or send it SIGTERM). The lab stops and removes every
container and the network it created, and keeps its two volumes, so the next `omniglass lab run`
picks up where you left off: a component you added is still there, and your secrets still decrypt,
because the server's encryption key lives in the data volume too. Press Ctrl-C a second time to
leave without cleaning up; a lab stopped that hard, or killed outright (SIGKILL, a closed laptop
lid), is cleaned up by the next run before it starts.

`omniglass lab run --fresh` removes both volumes first and starts over from the seed. Use it after
pulling a change whose seed or schema an old lab cannot carry forward: lab data is disposable.

The node is enrolled afresh on every run (its token re-minted), so the lab stores no node secret.

Only the console is published, on `127.0.0.1` (`127.0.0.1:8080` by default). The database, the
server's bus and the node publish nothing; the node reaches the server across the lab network.
`NET_ADMIN`, root and the ping sysctl are held by the `node` container alone, for the simulator's
impairments and truthful ping, and they reach only that container's own network namespace, never
your machine's. The `server` and `db` containers carry no added capability.

How often the node checks in, pulls its worklist and probes is its **cadence profile**. Your lab
runs at `lab`: it checks in often and pulls its worklist every few seconds (`--worklist-every`), so
a change you make in the console reaches it within seconds, and probes reachability less often
(`--probe-every`), because a lab may run for days and a probe every 2s wrote most of its rows.
Each probe and each poll runs on its own interval, on the node's own timer, not on the check-in.
The throwaway lab each walkthrough is recorded on runs at
`walkthrough` and probes every 2s, since a recording is held to a time budget, so in your
lab a walkthrough that waits on a probe's verdict (watching a rule raise an alarm, say) waits a few
seconds longer than its recording. Its seed also sets the platform's report window
(`collection.report_seconds`) to 10s, so the node's and the server's own figures, the ones
[Platform health](/guides/operator/platform-health/) reads, land inside the recording; your lab
reports at the platform's 60s, so those figures take up to a minute to appear. `default` is the product's own cadence, what a deployment's
node runs at; the [lab footprint](/contributing/test-driven/#measuring-a-running-lab) measures a lab
at each to say what that cadence costs.

<LabTopology part="cadences" />

Publishing nothing is not the same as unreachable. On Linux, a Docker bridge network's addresses are
routable from the machine itself, so a local process that finds the lab network's address can reach
the database there, with the lab's fixed Postgres login (`omniglass` / `omniglass`, a superuser of
that database and so of its container). That is the lab's data and the lab's container, both
disposable, on a machine you share only with people you would hand the console's well-known login
to anyway; it is one more reason a lab is never a place for real data.

## Safety rails

A lab's login is well known and its data is disposable, so it is kept apart from anything real:

- **Loopback only.** The console is published on `127.0.0.1`, reachable from this machine alone.
  `--listen` moves it to another address, and the lab then says, once it is ready, that anyone who
  can reach that address can sign in with the well-known login.
- **It says it is a lab.** The server runs in lab mode, a setting only `omniglass lab run` passes,
  and reports it on `GET /auth/status`; the console shows the **Lab instance** banner on the sign-in
  page and in the shell.
- **Lab and real databases refuse each other.** The lab writes a mark into the database it creates.
  A server outside lab mode refuses a database that carries the mark, and a lab refuses a database
  that holds data and no mark (a real deployment's). Each refusal says why and what to do. The mark
  is data the lab writes, never a migration or a boot-seed row.
- **A local daemon only.** The lab refuses a Docker daemon on another machine, where the loopback
  publish would land on that machine and not this one.
- **One lab at a time.** A run refuses to start while another lab is running here (or was started
  from another machine, or from inside a container, on the same daemon), and never touches it; a run
  that fails to come up removes only what it created itself.

## Flags

The [CLI reference](/reference/cli/#omniglass-lab-run) renders every flag and its default from the
command itself; here is when you would reach for each:

- `--port` moves the console off 8080 when something else holds it. A taken port fails before
  anything is created, rather than silently picking another, so the address you bookmarked survives
  a restart. `--port 0` lets Docker pick a free one, and the ready line prints it.
- `--listen` publishes the console on another address of this machine, to show a lab to someone on
  your network. It exposes the well-known login with it, and the lab says so.
- `--fresh` starts over from the seed, removing the lab's data first.
- `--scenario` picks another fleet for the lab's first run (the [seed-dev reference](/reference/cli/#omniglass-seed-dev) lists them:
  an empty install, the dev fleet having a bad day, the dev fleet at enterprise size). On a lab that
  already has data, pair it with `--fresh`.
- `--image` runs an omniglass image of your choosing, with a warning: a lab whose server and binary
  disagree is yours to debug.

- `--systems` and `--plan` size a [scale lab scenario](#scale-lab-scenarios) instead of a seeded
  fleet, and preview it with its preflight.
- `--keep` keeps a scale lab's data when it stops, for a run that lasts days ([a soak
  run](#a-soak-run)). A seeded fleet's lab keeps its data already, so it refuses the flag.

A few more flags are hidden from the help because they are for scripts, not for you: the repo's
own browser tests, docs screenshots, demo recorders and probe each bring up a throwaway lab of their
own through them (a project of its own whose data goes when it stops, held for the script, or one
whose fleet has no node collecting from it, so the pages the docs photograph hold still). The
[demos guide](/contributing/demos/) says how the repo uses them.

**Which image runs.** A binary built by `make` runs the `omniglass:dev` image the same `make` built:
the image carries its build id in the OCI label `org.opencontainers.image.version`, and the lab
refuses an image whose label is not its own build id, saying to run `make`. The lab never builds
anything itself, so it always runs the code you built. A release binary runs
`ghcr.io/hyperscaleav/omniglass:v<version>`, pulled if absent
([container image](/guides/container-image/#where-it-ships)).

## Scale lab scenarios

The dev fleet is one fixed size. The [scale lab](https://github.com/hyperscaleav/omniglass/issues/1357) asks how the platform behaves at 100, 1,000
and 3,000 systems, so it describes an environment once and sizes it with a knob: a **scenario
manifest** names its kinds of site (one headquarters and the offices repeated around it), the
buildings each kind's rooms sit in, the standards placed at each kind as ratios, and the product
filling each role of each standard. The size picks how many sites there are as well as how many
systems, so a bigger plan is more nodes rather than bigger ones. One manifest ships today, `corporate`
(a headquarters with regional and branch offices of huddle rooms, meeting rooms, divisible conference
rooms and lobby signage), in
[`internal/lab/scenario/manifests/`](https://github.com/hyperscaleav/omniglass/tree/main/internal/lab/scenario/manifests).

Run a scenario at a size, and the lab brings it up as a distributed deployment: Postgres, the
server, and **one node container per site**, each enrolled with its own token and running the
simulator in its own process for that site's components. Every simulated component answers on its
own loopback address, so a site looks like many devices rather than many ports on one address. The
lab is up once every site's node is collecting from every component (the planted faults aside).

```sh
omniglass lab run --scenario corporate --systems 100
```

A scale lab is its own Docker project, `omniglass-scale`, so it runs beside your learning lab, and
it is throwaway: Ctrl-C removes every container, network and volume it started. With `--keep` it
keeps its two volumes instead, the way the learning lab does, and the stop line names the command
that picks it up again: the same scenario, size and `--keep` (and its `--project`, when not
`omniglass-scale`). The next run re-attaches the volumes, keeps the fleet it seeded rather than
seeding again, and enrolls each site's node afresh; a kept lab started at another scenario or size,
or without `--keep`, is refused, naming `--fresh` to start over. Add `--plan` to
print what a size would build without starting anything: three tables (each archetype's sites,
floors per site, systems of each standard and totals; each site's systems and components; the
components of each product) and the [preflight](#how-big-a-lab-your-machine-can-run). Without
`--systems`, a scenario asks for a size (one system per site at the fewest sites, up to 10,000).

### How big a lab your machine can run

The scale lab is meant for a developer machine, and it assumes no particular size: before it starts
anything it estimates what the size needs, compares it with what the Docker host reports, and
refuses a size that does not fit, naming the largest that does. It plans on at most 80% of the
host's memory and CPUs, leaving the rest to your desktop and the daemon. The estimate is three costs,
measured with `docker stats` at 20 and 100 systems and kept in `lab.MeasuredCost`:

- **the server and Postgres**, paid once: about 170 MiB and a twentieth of a core;
- **a node container**, paid once per site (up to 30 times): about 36 MiB and a hundredth of a core;
- **a simulated component**, its simulator's share and the collection from it: about 0.9 MiB and a
  thousandth of a core.

So `corporate` at 1,000 systems (18 sites, 3,016 components) needs about 3.4 GiB and 3.2 cores, and at
3,000 (30 sites, 8,950 components) about 9.1 GiB and 9.3 cores. CPU, not memory, is what runs out
first on most machines: the reference WSL setup of 12 GB on a 12-core host fits 3,000 systems only
just. `--plan` ends with the decision for this machine:

```text
Preflight: about 3.4 GiB of memory and 3.2 cores (the server and Postgres, a node for each of 18 sites, 3016 simulated components).
This Docker host can spare 25.1 GiB and 9.6 cores (80% of its 31.3 GiB and 12 cores).
Decision: fits.
```

A size that does not fit exits non-zero before it creates a container, saying why and what does:

```text
error: A scale lab of 1000 systems (18 sites, 3016 simulated components) needs about 3.4 GiB of memory and 3.2 cores; this Docker host has 2.0 GiB and 12 cores, of which the lab plans to use at most 80%.
  To fix it: run --systems 447, the largest that fits, or give Docker more memory or CPUs.
```

That one was forced with the hidden `--host-memory 2g`, which plans against a memory limit of your
choosing, so you can see where a smaller machine's ceiling sits without one. The estimate is a
model, not a promise: it was measured at small sizes, and [`omniglass lab measure`](#measuring-a-scale-lab)
measures a running lab.

**A bring-up never hangs.** It is bounded by a timeout (20 minutes, or the hidden `--ready-timeout`),
the seed included. Past it the lab removes everything it started and names what was not up: each
site whose simulator never connected, and each site's components not up yet, by name and loopback
address.

`make scale-lab` (with `SYSTEMS=100` and `SCENARIO=corporate` by default) runs the check the scale
lab is proven by: it brings a size up through `bin/omniglass lab run`, asserts one node container per
site and every component at its own loopback address, prints the containers' memory and CPU, and
stops the lab, asserting it left no container or network. It builds the image and stands up real
containers, so it is not part of `make test` or CI.

A plan seeds as configuration rows through `devseed.SeedPlan` (`internal/devseed/plan.go`), the one
entry point the scale lab's bring-up calls: the sites, buildings, floors and rooms, the systems in the
rooms, the components filling each system's roles, and the simulated endpoints on them, each site's on
that site's node (`PlanOptions.NodeFor`; `Node` alone puts them all on one). It drives the
Gateway's own create methods, one row per transaction, so names, labels, audit rows and derived health
come out as they do for an operator's writes, and the same plan always lands the same names and
addresses. It seeds no metric history. Measured on a shared worker, the corporate plan takes about 12
seconds at 100 systems and 2 minutes 13 seconds at 1,000, most of it the health recompute each role
assignment triggers rather than round trips ([#1562](https://github.com/hyperscaleav/omniglass/issues/1562)).
`PLAN_MEASURE=100,1000 go test -run TestPlanSeedMeasure ./internal/devseed/` reproduces the table.

### Measuring a scale lab

`omniglass lab measure` says what a fleet of a size costs to run: one table, measured over a window you
state, from a running scale lab. It is diagnostic and never a gate (ADR-0094): on a shared host the
figures move with the neighbours, so compare runs from one machine. It is outside `make test` and CI.

```bash
make scale-measure SYSTEMS=100                                    # brings a lab up, measures it, removes it
./bin/omniglass lab measure --systems 100 --warmup 2m --window 3m # the same, with the window chosen
./bin/omniglass lab measure                                       # measures the scale lab already running
```

With `--systems` it brings up a throwaway scale lab, waits for it to be ready, lets it run for `--warmup`
(the first minutes are a burst, every node's first collection), measures for `--window`, removes the
lab and checks nothing is left. Without it, it measures the scale lab you started with
`omniglass lab run --scenario corporate --systems N`; that lab must be one this build started, because
the ingest lag reads the commit times Postgres records only when the lab asks it to
(`track_commit_timestamp`), and a lab started before that says so and stops. It writes the same figures
as JSON (`--json`, `lab-measure.json` by default, empty for none), so two runs diff.

Every flag, its default and its meaning is in the generated
[CLI reference](/reference/cli/#omniglass-lab-measure), which `make gen` writes from the command itself.

How to read each row:

- **metric rows a minute, property rows a minute**: rows inserted per minute over the window, from the
  database's own insert counters, so they count every writer (the ingest consumer, the rules that
  calculate metrics, the server). The first is the lane the collection fills.
- **metric rows a day, metric table a day, property table a day, receipts a day, database a day**: the
  window's growth multiplied up to 24 hours. Row counts are inserts; the table figures are the
  relation's size on disk including its indexes, so they step in 8 KiB pages: a lane that grows
  by less than a page in the window reads `0 B`, and a short window is coarse. Receipts are the bus
  consumer's delivery receipts (`telemetry_receipt`, which make a redelivered batch land once and
  carry each batch's delivery ledger and outcome, the delivery table's source), and
  the database line is the whole database, so it also carries the logs and anything else that grew. A daily-partitioned lane
  is one relation per day, so its growth is the sum across them. Extrapolation assumes the window is
  steady: a window that includes a burst reads high.
- **batches landed, samples landed, samples per batch, batches a second**: the receipts the window
  inserted (one per batch the ingest consumer landed), the metric and property rows it inserted, their
  ratio, and the receipts over the window's seconds. A node sends one batch per tick with a group per
  task, so samples per batch grows with the tasks a node runs; a figure near one means batches are not
  being coalesced. The rows count every writer, as the per-minute rows do, so the ratio reads a little
  high in a lab that calculates metrics. The receipt count is Postgres's inserted-tuples counter, which
  also counts a receipt whose transaction rolled back, so a batch the consumer landed in three passes
  after a Postgres refusal counts three, and samples per batch reads low under a refusal storm.
- **WAL a day**: the write-ahead log written during the window (the difference between two log
  positions), multiplied up to a day. It is what replication and backups would carry, and is usually
  more than the tables, since every change is logged and indexes are logged with it.
- **WAL a sample**: the same WAL delta divided by the samples the window landed, the figure that
  sizes replication and backups per device rather than per day. It carries every writer's WAL (the
  receipts, the calculated metrics, the server's own rows), so it reads a little high for the raw
  lane alone; a figure far above the row's width is index and receipt cost, not the sample.
- **database size, metric partitions, metric blocks and trends, dead tuples**: what the database holds
  at the window's end, where the rows above are what it gains. The size is the whole database; the
  partitions are the metric lane's daily partitions and the day the oldest starts, so retention is
  keeping up when the oldest day moves forward and the count stays level. The blocks and trends are
  the bytes of the two rollup tables. The dead tuples are the rows deleted or updated in `property`,
  `log_line` and `node_log` that vacuum has not yet reclaimed, summed over their partitions; a count
  that only climbs across a sampling run is vacuum falling behind. Each is a level, not a rate, so one
  run reads one point, and [a sampling run](#sampling-a-scale-lab-over-time) reads its trend.
- **`<container>` cpu, memory**: each container's CPU in millicores (a thousand is one core) over
  the window, from the cgroup's CPU time, and its working set (anonymous plus shared memory, the part
  not reclaimable as page cache). One line each for the server, Postgres and every node, then the
  total. A node is one site's simulators and its collection, so its cost is what that site's devices
  add; the server and Postgres are what every site's writes add up to.
- **ingest lag p50, p95, p99**: the time from a sample's probe (the timestamp the node gave it) to the
  commit of its row, over the newest observed metric rows the window landed (up to 20,000, the count is
  shown). It includes the node's batching, the bus, the consumer and the insert. Percentiles are
  nearest-rank; the p99 is the figure the [scaling targets](/architecture/scaling/#ingest-one-batch-per-tick)
  hold the ingest path to. A node flushes its spool once a second, so a lag near one second with a
  flat tail is the spool wait, not a queue. It is not network time to a real device: the simulators
  answer from the same host.
  When no sample probed inside the window had committed by its end, all three cells read `not measured`:
  landing has fallen further behind than the window is long. The table then ends with the reason and
  how long before the read the newest row committed and its sample was probed, and, if that sample was
  probed before the window began, `ingest lag exceeds the window` with how long before the window's end
  it was probed. That is an ingest finding, not a blank; the JSON carries the same under
  `ingest_lag_not_measured`, and every other figure is still reported.
- **consumer redeliveries**: batches the ingest consumer could not confirm and the bus handed it again
  (`unconfirmed acks`), and messages it dropped after repeated failures (`abandoned`), counted from
  the server's log since the window began. A redelivery that succeeds the second time logs nothing, so
  this is a floor: zero means none was logged, not none happened. Anything above zero in a quiet lab
  is worth a look.
- **consumer lane busy**: how much of the window the ingest consumer spent inside its handler, landing
  batches. The telemetry stream is a work queue with one durable consumer and one message in flight,
  so the consumer is one lane, and its busy fraction is the lane's utilisation: at 100 % every batch
  waits for the one before it and lag grows without bound; at 25 % the lane could carry four times the
  load before it saturates. The row also gives the service time a batch (busy time over batches) and
  the batches it counted over the span. The server tallies every batch's handler time and logs the
  cumulative count and busy milliseconds every 30 s (`msg="ingest lane"`, only when the count moved,
  so an idle server is quiet); the harness reads the first and last tally inside the window and
  divides the busy time between them by the time between them, so the fraction is exact to the
  millisecond over that span and no boundary estimate is needed (a batch in flight at a tick counts
  toward the next interval). It needs two tallies inside the window, 30 s apart: a window too short
  to hold two ticks, a lane that was idle at a tick, or a server built before this line reads
  `not measured` with the reason under the table, as does a tally that went backwards (the server
  restarted inside the window). Together with the lag this answers
  whether more consumers would help: a lag at the spool wait with a lane mostly idle means the lane is
  not the bottleneck.
- **fleet view p50, p95**: the time of `GET /api/v1/views/fleet`, the whole-fleet view the console
  opens on, read through the API with a token the harness mints, spread evenly over the window so it
  is read while the lab collects, not while it idles. The reads are sequential, so these are one
  user's response times, not a load test.
- **system page p50, p95**: the time an operator waits for the console's system page, with
  `--page-clients N` (0, the default, skips it and the rows read `not measured`). A load is every read a
  cold open of the page makes, all at once as the browser makes them, timed from the first request to
  the last answer: the catalogs it labels with, the system, its health, members, roles and metrics, and
  then one 24 hour series read for each chart the metrics answer names. N clients each make
  `--page-loads` loads spread over the window, staggered so their loads overlap, against the system
  `--page-system` names or the fleet view's first. A load where any read does not answer 200 is an
  error, kept out of the times and counted in the p95 row and as `system_page_error_ratio` in the JSON,
  0 when every load answered. The page's own test fails when the page gains or drops a read this list
  lacks, so the load cannot drift from the page. The alarms, events and logs are not part of it: the
  page reads them only when its activity tab is opened.
- **retention drain**: how fast the retention pass deletes rows past their window. After the window
  the probe plants aged property rows (`--backlog`, each with a newer row of its own series, which
  the prune requires), restarts the server so its pass runs at start, and reads the count of rows
  left every half second. The rate is rows deleted over the span deletes were seen in; the time before
  the first delete (the restart and the pass's startup) is shown apart as `after N s to start`. A
  backlog above one pass's budget (200,000 rows) is a rate over the first pass, the rest left for the
  next. It measures the property lane, whose retention deletes in chunks; the metric lane's retention
  mostly drops whole daily partitions, which has no rate to read. The probe removes its rows when it
  is done, and `--backlog 0` skips it, leaving the server running as it was.

#### Every request reached its endpoint and was answered

Below the table, an **endpoints** block closes the loop: what every node sent, what each simulated
endpoint saw arrive and how it answered, and what landed in the database, reconciled hop by hop.
Each node is read through `GET /nodes/{name}/simulation/observation` at the window's start and at its
end, and each read is a bracket of three (the simulator, the node, the simulator again; see
[what an endpoint observed](/architecture/simulation/#what-an-endpoint-observed)). The start's
reads follow a read of the database's clock and the end's precede one, so the telemetry receipts
that clock bounds fall inside the reads. Per protocol it prints:

- **received**: the requests the node's simulators saw arrive over the window, beside how many
  **poll targets** the window should have drawn on that protocol at least twice (each enabled poll
  task's endpoint, at the interval its node actually runs it: a driver poll at its function's
  schedule, a reachability probe at the node's probe interval), the connections accepted, and each
  outcome. Many http requests read `refused`, which is not a loss: a digest-authenticated device
  answers each first request 401 before the one that carries the credentials, as real gear does.
- **service time**: the simulators' own time to answer, p50, p95 and p99, merged over the nodes.
- **overlap-ratio**: the share of requests that found their face already serving one. A node sends a
  face one request at a time, so anything above zero is a finding; the five worst faces since each
  simulator started are named under the block.
- **in flight high** and **arrival high**: the most requests a node's simulators held at once, per
  protocol and over all of them, beside the node's dispatch gauges once a pool reports them.

Then one line per gap, in the order a request travels:

| Gap | Lost means | Masked by |
| --- | --- | --- |
| `connect-not-accepted` | a connection the node opened that no simulator accepted | connections still in the kernel's backlog at the end read |
| `sent-not-received` | a request whose bytes left the node and never arrived | requests in flight at the node's end read |
| `received-not-settled` | a request a simulator received and never settled | |
| `answered-not-returned` | an answer a simulator gave that the node never got | answers in flight, answers late past the node's timeout (shown as `answered late`), and traffic on the protocol the node does not tally yet (#1661) |
| `published-not-landed` | a batch the bus acknowledged with no receipt in the database | receipts landed in the 30 s before the window (the bus's acknowledgement wait), before the ingest lane drained past the start read (batches from before the window), or after its end |
| `spool-dropped` | a batch the node's spool gave up on | |
| `unhit-endpoint` | a poll target due at least twice whose device saw nothing on its protocol | devices past the simulator's sample of twenty, not checked against the targets (#1663) |

Every figure is a lower bound: positive only where something was lost, with what could hide a loss
printed beside it as `masked`, never folded into it. A clean run reads `0 lost` on every line.
A loss is named per node under the totals, with the protocol and, for an unhit endpoint, the
component. An icmp target reads `not observed by the sim`, since the kernel answers a ping. A node
whose simulator carries an applied impairment reads `impaired` instead of lost on every gap (an
impairment loses traffic on purpose; telling it apart per protocol is #1662), and a node or
simulator that restarted inside the window reads `restarted`, since none of its figures compare.
The window is refused past 23 hours, since the server prunes receipts at a day. Each mark waits for
the ingest lane to land a sample a node probed after it, so a lagging lane delays the count rather
than reading as a lost batch. When the block cannot be read (a simulator or node not answering, or
a lane still behind three minutes after a mark) the table ends with
`endpoints not measured` and why, and the JSON carries it as `endpoints_not_measured`; every other
figure is still reported.

#### Reading the delivery table

Below the endpoints block, the delivery table says how much telemetry the lab lost on the way in, as a
**loss ratio** per kind per hop, `(in - out) / in`, read the same way for every kind
([messaging](/architecture/messaging/#accounting-every-item-the-loss-ratio)). A healthy lab reads
exactly 0 for every kind:

```
delivery    hop     in       out      loss     dedup  cause
metric      ingest  1275     1275     0        0      -
property    ingest  166      166      0        0      -
event       ingest  0        0        -        0      -
log         ingest  0        0        -        0      -
end to end  metric 0  property 0  event -  log -
```

- **in** is the items the node minted in the window (the batches' ledgers, plus the items of any batch
  that never landed), **out** the items accounted for (`stored`; for properties `coalesced`, an
  unchanged value skipped on purpose; and `unbound`, an identity no binding places, which the
  conduit's unbound inbox holds for the operator to assign). A kind with nothing in reads `-`, never 0. Only the ingest hop
  is read today; the node, schedule and sim hops follow.
- **dedup** is the items a redelivery carried again, which the receipt absorbed. It sits beside the
  ratio, never in it, so a retry storm never moves the loss off 0.
- **cause** is the largest outcome behind a loss: a `refused-<why>` (a key not registered, a writer or
  instance refused, a value invalid or empty, a group the gateway refused), `orphaned`,
  `unidentified`, or `missing`. An `unbound` identity is not loss: the operator has not assigned it,
  and the inbox already shows it, so the dev seed's deliberately unbound `zr-boardroom-b` reads 0. A refusal is loss on purpose: the sims emit
  only valid keys, so any refusal in a lab is a bug worth chasing. The JSON (`delivery`) carries every
  outcome's count on every row, with the same keys for every kind.
- **missing** is a batch that never landed: a hole in a node boot's batch sequence, its items read
  from its neighbors' offsets. At this stage it cannot say why; the footer reads `never landed:
  Termed at ingest, dropped at the node, or lost in between`.
- **end to end** is each kind's loss over every hop it crosses, `1 - prod(1 - loss)`; with one hop it
  equals the ingest row.
- **unsettled** names a node boot whose window's batches were not all known when `--settle-timeout`
  ran out (no later batch said the spool had cleared past them, or the stream still held batches),
  with no ratio for it rather than a guess. A note under the table gives the stream's pending and
  unacked counts when the stream was the cause.

Two limitations, both closed by the node hop (#1692):

- A node killed while it still holds unshipped batches loses its old boot's tail, and nothing later
  in that boot reveals it.
- `missing` also counts batches the node's spool dropped (an overflow, a bus refusal), which take a
  sequence number and never ship.

The same 23-hour window limit applies, since receipts are kept a day. A lab
whose server predates the ledger reads `delivery not measured` with the reason, and every other figure
is still reported.

The window and the warm-up are printed above the table, and belong beside any figure you quote from it.

### Sampling a scale lab over time

One window says what a fleet costs now; whether growth, retention and vacuum keep up shows only over
hours. `--every` samples the running lab on an interval instead, one compact JSON line a sample:

```bash
./bin/omniglass lab measure --every 10m --window 5m --append scale.jsonl --page-clients 4
jq -r '[.seq, .ingest_lag_ms.p95, .system_page_ms.p95, .absolutes.dead_tuples.property] | @tsv' scale.jsonl
```

The lab is found, signed in to and warmed up once; then every `--every` one window is measured. Each
line carries the one-shot report's fields at the same paths `--json` writes them, so a query written
against one measurement reads every sample, plus `seq`, `at` (when the window closed) and
`uptime_seconds` (how long the server had been running then, so a series whose uptime falls was
measured across a restart). `--append` opens the file for append, creating it if missing, so a series
stopped and started again continues the same file; without it the lines go to standard output.
`--samples N` stops after N samples, and 0 samples until interrupted: the first Ctrl-C or SIGTERM lets
the sample in flight finish and write its line. A sample that fails writes a line with its `error` and
no figures, and the run goes on, so a gap in the series is visible rather than missing. Each sample
also reads the endpoints block and the delivery table; the delivery read's `--settle-timeout` wait can
run a sample past `--every`, and the next one then starts at once rather than skipping its slot.

Sampling never restarts the server: it skips the retention probe, `--backlog` defaults to 0, and a
`--backlog` you give is refused, as are `--systems` (sample a lab you brought up), an `--every`
shorter than the `--window` it measures, and `--json`. The schedule's health on the nodes and command
latency are not in a sample yet (#1625, #1626).

### A soak run

A soak run holds a kept scale lab up for days, at production cadence, under a service manager, with
the sampler writing one line every interval: the evidence of whether growth, retention and vacuum
keep up. It runs on a host of its own, so nothing else competes for the machine it measures.

**Pin the build.** A soak measures one build. Build its image once and give it a tag of its own,
named for the commit (`omniglass:soak-<shortsha>`), and run the binary built from the same commit:
`--image` runs a server the binary does not check against itself, and a shared tag rebuilt mid-soak
would measure two builds in one series.

**The lab unit.** The service manager starts the lab, restarts it if it fails, and stops it with
SIGTERM, which the lab treats as Ctrl-C: it removes its containers and network and keeps its volumes,
so the restart picks up the same fleet and data. A systemd unit:

```ini
[Unit]
Description=omniglass soak lab
After=docker.service
Requires=docker.service

[Service]
ExecStart=/usr/local/bin/omniglass lab run --scenario corporate --systems 3000 --cadence default --keep --image omniglass:soak-<shortsha>
Restart=on-failure
RestartSec=30
# SIGTERM to the lab alone; it stops its containers and keeps its volumes.
KillMode=mixed
TimeoutStopSec=5min

[Install]
WantedBy=multi-user.target
```

**The sampler unit.** The sampler runs beside the lab, bound to it, and appends to one series file,
so a sampler restarted mid-soak continues the same series:

```ini
[Unit]
Description=omniglass soak sampler
After=omniglass-soak-lab.service
BindsTo=omniglass-soak-lab.service

[Service]
ExecStart=/usr/local/bin/omniglass lab measure --every 15m --window 5m --append /var/lib/omniglass-soak/series.jsonl --page-clients 4
Restart=on-failure
RestartSec=60

[Install]
WantedBy=omniglass-soak-lab.service
```

A sample taken while the lab restarts writes its `error` line and the series goes on; the restart
shows as `uptime_seconds` falling.

**Retention inside the run.** A soak shorter than the retention windows never sees retention remove
anything. Once the lab is up, shorten the metric window so the run crosses it: retention's
`metric_days` on **Admin > Settings** ([how long data is kept](/guides/admin/#how-long-data-is-kept)),
or over the API with a token of the lab's:

```sh
curl -X PATCH "$OMNIGLASS_SERVER/api/v1/settings/retention" -H "Authorization: Bearer $OMNIGLASS_TOKEN" \
  -H 'Content-Type: application/merge-patch+json' -d '{"metric_days": 2}'
```

The setting lives in the kept database, so it survives the lab's restarts.

**Reading the series.** Each line reads at the same paths as one measurement. One row a sample (a
failed sample's `error` line skipped): when, the build, ingest lag p95, system page p95 (ms), database
bytes, metric partitions and the server's memory (MiB):

```bash
jq -r 'select(.error == null) | [.at, .build, .ingest_lag_ms.p95, .system_page_ms.p95,
  .absolutes.database_bytes, .absolutes.metric_partitions,
  (.containers[] | select(.name == "server") | .working_set_mib)] | @tsv' series.jsonl
```

The first sample beside the last states the growth over the run:

```bash
jq -s 'map(select(.error == null)) | first, last | {at, build, lag_p95: .ingest_lag_ms.p95,
  page_p95: .system_page_ms.p95, database_bytes: .absolutes.database_bytes,
  metric_partitions: .absolutes.metric_partitions,
  server_mib: (.containers[] | select(.name == "server") | .working_set_mib)}' series.jsonl
```

With the metric window at 2 days, retention drops its first partition on day 3, and from then the
partition count should stop growing.

**Upgrading mid-soak** keeps the data and the series: stop the sampler and the lab, install the new
binary and its pinned image, point the lab unit at the new tag, and start both again. The kept fleet
carries over (the seed migrates the database on every start), and the sampler appends to the same
file, so the series goes on under a new `build`. To split it at upgrades, list the builds in order
with how many samples each took:

```bash
jq -r 'select(.error == null) | .build' series.jsonl | uniq -c
```

A build whose scenario plan differs at the soak's size (its manifest or catalog changed) is refused by
the kept check, and so is a rollback across a schema change, since migrations only move forward: both
need one run with `--fresh`, which seeds the fleet over, so start a new series file with it.

**Looking at it.** The lab publishes its console on the host's loopback only; reach it from your own
machine through a tunnel, then open `http://127.0.0.1:8080/web`:

```sh
ssh -L 8080:127.0.0.1:8080 <soak-host>
```

### The manifest format

```yaml
name: corporate                 # the scenario's name, what --scenario takes
label: Corporate
sites: { min: 3, max: 30 }      # the fewest and the most sites, whatever the size
standards:
  - name: mr65                  # a standard template from the catalog
    system_type: meeting        # a registered system type
    products:                   # role -> catalog product
      video-bar: kestrel-vroom
      main-display: boreal-edge-65
      touch-control: newtron-panel-7
      scheduling-panel: newtron-slate-5
archetypes:
  - name: hq
    label: Headquarters
    headquarters: true          # placed exactly once, under its own name
    typical_systems: 250        # how many systems a site of this kind typically has
    buildings:
      - { name: tower, floors: 30 }
    systems:                    # standard -> ratio, in tie-break order
      huddle-room: 30
      mr65: 20
  - name: branch
    label: Branch Office
    weight: 2                   # this kind's share of the sites besides the headquarters
    typical_systems: 25
    buildings:
      - { name: main, floors: 3 }
    systems:
      huddle-room: 40
      mr65: 25
```

The vocabulary is the platform's own, so a scenario never invents a device. Each standard is a
[standard template](/architecture/templates/) and staffs its roles the way a system template does, through
the same planner: a role with a quorum of two takes two of its product, and a choice is answered by
naming the roles of one alternate. Every product is a catalog product a simulator profile serves, so
the lab can simulate every component it plans. Exactly one archetype is the headquarters, which takes
no weight; every other archetype repeats and takes one. The site bounds must have a minimum of at least
one and a maximum no lower than the minimum. The validator collects every problem at once and names
each with the manifest line to fix:

```text
corporate.yaml:21: sites max 3 is below min 5
corporate.yaml:57: product "polaris-sky-c6" has no simulator profile, so the lab cannot simulate it
corporate.yaml:65: unknown product "boreal-cast-m9": the catalog has no product of that name
```

### How many sites

`--systems N` first picks the number of sites. The **average repeated site** is the repeated
archetypes' `typical_systems` averaged by their weights. The plan has the headquarters plus one site
for each average repeated site's worth of systems beyond the headquarters' `typical_systems`,
rounded half up, then clamped to the manifest's `sites` bounds:

```text
sites = clamp(1 + round((N - hq typical) ÷ average repeated site), min, max)
```

The count never falls as N grows. The headquarters is placed once and the other sites are shared
among the repeated archetypes by weight, by the largest remainder method described below. A
repeated archetype's sites are numbered from its name in order (`regional-01`, `branch-12`), so the
same N always gives the same sites.

For `corporate`, the headquarters typically has 250 systems, a regional office 80 and a branch 25,
with two branches for every regional office, so the average repeated site has about 43 systems:

| `--systems` | Sites | Headquarters, regional, branch |
| --- | --- | --- |
| 100 | 3 (the minimum) | 1, 1, 1 |
| 1,000 | 18 | 1, 6, 11 |
| 3,000 | 30 (the maximum) | 1, 10, 19 |

The minimum of 3 keeps a small plan a headquarters and two offices; below 359 systems the formula asks for
fewer and the minimum holds. From 1,485 systems the count is at its maximum of 30, so larger sizes
grow the sites instead.

### How a size is split

The systems are then split twice, both times by the **largest remainder** method in exact
whole-number arithmetic. Each share first takes the whole part of its exact quota, and the
systems left over go one each to the largest fractional remainders, a tie going to the one written
first.

1. Across the sites. Each site first takes one system, and the remaining `N - sites` are split by
   each site's `typical_systems`, in plan order (archetypes as written, each archetype's sites in
   number order).
2. Within each site, its count across its archetype's standards by ratio.

So the plan always has exactly N systems. Each site is within one system of its exact share (one, plus
its typical-size share of the rest), and each standard at a site is within one of its exact share of
that site. Fleet-wide, a standard is within two systems per site of its exact share of N (at 30 sites,
within 60). A small N can round a rare standard at a small site to zero; that is the rule, not a bug.

Each site's systems are then placed in its archetype's standard order, round-robin over its floors
(buildings in order, floors bottom up), so system `j` of a site with `F` floors sits in room
`j ÷ F + 1` of floor `j mod F`: every floor fills evenly. A system is named `<site>-<standard>-<k>`,
its room `<site>-<building>-<floor>-<room>`, and it takes a friendly label from the same name
generator the simulator's fleets use, seeded from the scenario, site, standard and index, so the same
manifest at the same size always resolves to the same plan.

## Why Docker is required

A lab is worth running only if collection behaves as it does against real gear: every component
answers on its own address, ping tells the truth, and an unplugged component goes dark. Each of
those leans on Linux networking that a bare binary on a workstation does not get:

- **Every simulated component has its own address**, one each in `127.60.0.0/16`. Linux treats all
  of `127.0.0.0/8` as local; macOS answers only `127.0.0.1` until each address is aliased with
  `sudo ifconfig lo0 alias`. Windows binds any `127.x` address without aliasing.
- **The ports are the profiles' real ports**, and some are privileged (SNMP 161, SSH 22, HTTP 80,
  HTTPS 443), because the seeded endpoints target them. Binding below 1024 needs a privilege on a
  Linux host.
- **Ping needs a kernel grant, and tells the truth only behind a firewall rule.** The node's pinger
  is unprivileged datagram ICMP: Linux allows it only where `net.ipv4.ping_group_range` admits the
  process's group, macOS allows it, and Windows offers no unprivileged ICMP socket. Even with the
  grant, every loopback address answers ping, component or not, until a firewall rule drops echoes
  to addresses that are no component, and that rule needs `NET_ADMIN`.
- **Impairments rewrite the network namespace.** Unplug, latency, jitter, loss and rate are an
  nftables table and traffic shaping on `lo`, applied with `NET_ADMIN`, and Linux only. On a
  workstation's own namespace they would reshape the whole machine's loopback.

Every container runs on a Linux kernel: natively on Linux, and inside Docker Desktop's VM on macOS
and on Windows (WSL2). So all of the above holds the same way on all three. Each container gets a
namespace of its own; Docker lets any user bind ports below 1024 inside one; the ping sysctl is set
per container, to a range that fits the groups rootless Docker maps, so the lab runs there too; and `NET_ADMIN` goes to the node's container alone, where it reaches only that
container. A native lab without Docker would need an admin prompt per address and a second
impairment backend on macOS, a privileged pinger and a third backend on Windows, its own namespace
plumbing on Linux, and an embedded Postgres everywhere, and would still behave differently on two of
three platforms. `make test` already needs Docker, so a contributor installs nothing new.

## When it will not start

Every check runs before the lab creates anything, and each failure exits non-zero, naming the cause
and the fix. The lab finds Docker the way the docker CLI does: `DOCKER_HOST`, then `DOCKER_CONTEXT`,
then the CLI's current context, then the platform's default socket or named pipe.

- **No Docker found.** Nothing answers at the default socket: install Docker Desktop (macOS,
  Windows) or Docker Engine (Linux), start it, and run the lab again.
- **Docker is not running.** The socket the context names does not answer: start Docker Desktop, or
  the service (`sudo systemctl start docker`).
- **Permission denied on the socket.** On Linux, add yourself to the `docker` group
  (`sudo usermod -aG docker $USER`, then sign out and back in), or use rootless Docker.
- **The console's port is taken.** Stop whatever holds it, or move the lab with `--port`.
- **The daemon is on another machine.** Unset `DOCKER_HOST` or `docker context use default`, or run
  the lab where the daemon runs.
- **A lab is already running.** Use that one, or stop it with Ctrl-C in its terminal.
- **The image is not built, or was built from another tree.** Run `make`, which builds the binary
  and the image together, then run the lab again. A binary built without `make` carries no build id
  and cannot tell which image is its own, so it asks for `make` too.

## The console fast loop

Working on the console itself, run the lab in one terminal and the console from source in another:

```bash
./bin/omniglass lab run       # terminal 1
cd web && npm run dev         # terminal 2: the console on http://localhost:5173/web, hot reload
```

The Vite dev server serves the console from source and proxies `/api` to the lab at
`http://127.0.0.1:8080` (IPv4 loopback, because the lab publishes on it alone). For a lab on
another port, point the proxy at it:

```bash
./bin/omniglass lab run --port 8081
OMNIGLASS_LAB_URL=http://127.0.0.1:8081 npm run dev
```

This loop needs Node; the lab itself needs only Docker. A change to the server, node or simulator
Go code is a rebuild instead: run `make` (the image rebuilds from cache) and then the lab again.
[Contributing](https://github.com/hyperscaleav/omniglass/blob/main/CONTRIBUTING.md) lists who needs
which toolchain, and the [design system](/contributing/design-system/#build-and-embed) covers how
the console builds.
