Identity and access decides who may call Omniglass and which slice of the fleet each caller sees and
acts on. It is enforced entirely in the application, in two layers, each held in one place. To
operate it, see [the admin Users page](/admin/users/) and [Access](/admin/access/).

## The two invariants

1. **A permission on every route.** Every API operation is either registered through one helper,
   `gated(op, resource, action)`, which installs the authentication and permission middleware ahead
   of the handler, or sits on a short, explicit allow-list of public and self-scoped routes. A route
   cannot be added ungated by omission: `TestEveryRouteIsGated` drives every operation in the
   generated OpenAPI with a signed-in user holding no permission and fails on anything but a 403
   outside that list.
2. **ABAC scope injected by the Storage Gateway on every query.** Every gateway method over a scoped
   resource takes the caller's resolved scope, `visible_set(P, action)`, as a required `scope.Set`
   argument and turns it into a parameterized filter on the row's owner. The
   [Storage Gateway](/architecture/storage/#the-storage-gateway-and-tiering) is the only path to the
   database (no row-level security, no PostgREST), so there is no unscoped path to forget.

The route permission is a fast reject, never the authorization: it asks only whether the caller holds
the action in **any** grant. The scope decides whether the caller may act on **this** row. A handler
that forgot its own check still could not query unscoped, because the scope is an argument the
gateway requires.

## Users and credentials

A **user** is who a role is granted to, identified by an opaque uuid, never an email or a name
([ADR-2036](/architecture/decisions/#adr-2036-the-iam-subject-is-a-user-a-person-or-a-machine)).
`users.kind` is one of two:

| kind | is | signs in with |
| --- | --- | --- |
| `person` | someone who signs in | a password and a session cookie, or single sign-on |
| `machine` | a script, an integration, or an outpost | a bearer token; an outpost its enrollment |

Each kind has a one-to-one detail table holding its own identifier, each unique, since each is the
only handle its user has and each is copied into the audit trail
([ADR-0111](/architecture/decisions/#adr-0111-a-service-accounts-identifier-is-a-name-and-it-is-unique)):
a person's `username`, a machine user's `name`, an outpost's `name` on its `outpost` row.

An AI is not a third kind. It acts as a person through an [agent token](#agent-tokens) that person
minted for it, with at most that person's authority.

### Credentials

A user holds any number of `credential` rows. `credential.kind` is `password`, `bearer` or `oidc`,
and `purpose` tells a `session` from a `token`:

| credential | kind | lifetime |
| --- | --- | --- |
| console session | `bearer`, purpose `session` | 12 hours, fixed |
| API or CLI token | `bearer`, purpose `token` | 90 days by default, at most 365 |
| password | `password`, one per person | argon2id, until changed |
| identity provider link | `oidc` | until unlinked |

- **A bearer token** is `ogp_<locator>_<secret>`: a prefix for secret scanners, a non-secret
  locator, and a 192-bit random secret. The server stores only its `sha256` and returns the token
  once, at mint. Every credential expires
  ([ADR-0019](/architecture/decisions/#adr-0019-every-credential-is-time-bounded-token-purpose-not-expiry-shape)),
  checked at authentication.
- **A password** is at least 12 characters, not on a common-password list, and does not contain the
  username (`auth.ValidatePassword`). Five consecutive misses lock the person for 15 minutes, refused
  with the same 401 as a bad password, so the lock is not an enumeration oracle; changing the
  password clears it. An admin reset can require a change at next sign-in, which refuses every route
  but the change itself until it is made.
- **Every bearer credential carries identifying metadata**: a description, the user agent and client
  address that created it, and when it was last used. The client address believes a forwarded header
  only from a configured trusted proxy (`OMNIGLASS_TRUSTED_PROXIES`)
  ([ADR-1185](/architecture/decisions/#adr-1185-the-client-address-believes-a-forwarded-header-only-from-a-configured-proxy)).

### Single sign-on

A person can sign in through an OpenID Connect provider
([ADR-2361](/architecture/decisions/#adr-2361-single-sign-on-links-a-person-to-an-identity-provider-subject-never-by-email)).
An `oidc` credential is a **link** from the person to the provider's subject: it holds no Omniglass
secret, only the provider's sealed refresh token, and a sign-in through it mints the ordinary
session. A link is made explicitly, by an admin under the takeover guard or by the person after
confirming their current password, never by matching an email. The sign-in is the code flow with
PKCE and a nonce derived from the browser binding rather than stored
([ADR-2362](/architecture/decisions/#adr-2362-a-sign-ins-pkce-verifier-and-nonce-are-derived-from-its-browser-binding-not-stored)),
and every call to the provider goes through the egress allow list. A sweep redeems each link's
refresh token every `sso.recheck_minutes` (15 by default) and revokes the sessions and tokens made
through it once the provider refuses. Owners keep password sign-in as break-glass.

:::design[Identity provider provisioning and SAML, tracked in #2364 and #2365]
A first sign-in provisions the person, and password sign-in can be reserved for owners (#2364); and
SAML 2.0 is a second protocol beside OpenID Connect (#2365).
:::

Provider groups map to Omniglass user groups so scoped grants follow the directory
([#2363](https://github.com/hyperscaleav/omniglass/issues/2363)): a groups-claim value keyed by issuer
maps to a `user_group` (`/user-groups/{group}/idp-mappings`, gated `user_group`). The sign-in and each
re-check refresh whose id_token carries the claim sync that issuer's `idp` memberships in their own
transaction, audited. The owner guard refuses both a mapping to a group with an owner grant and an
owner grant on a mapped group
([ADR-2363](/architecture/decisions/#adr-2363-an-admins-add-makes-an-idp-membership-local-and-a-groups-last-mapping-takes-its-idp-members-with-it)).

### Agent tokens

An **agent token** is a token type on the person's own credential, not a user of its own
([ADR-1179](/architecture/decisions/#adr-1179-an-agent-token-is-a-token-type-on-its-persons-credential-and-never-reveals)).
`POST /auth/me/tokens` with an `agent` name mints one; it always expires, and two fields narrow it:

- **`roles`**: the agent's own grant, **intersected** with its person's current permissions on every
  request (`rbac.Set.Within`), so narrowing or revoking the person narrows or stops the agent at its
  next call. The scope the gateway injects is the person's.
- **`channels`**: where the token is accepted (`api`, `mcp`), checked against the channel the server
  sets on the request, which no caller can claim.

**The plaintext ceiling.** An agent token never holds a `reveal` or `enroll` action, whatever its
roles: authentication strips them (`rbac.Set.Without`), so even an owner's `>` loses them, and the
same applies to any token used through MCP. An agent works with a credential only through routes that
use it server-side. Everything else its person may do, it may do
([ADR-2047](/architecture/decisions/#adr-2047-an-agent-may-do-what-its-person-may-except-take-a-credential-out-in-plaintext)),
including binding a secret to a target, which takes `secret:bind` for any caller. An agent token is
refused minting a token, changing a password, and impersonation. Every write it makes records its
person as the actor and the agent's name in the audit row's `agent`.

#### MCP clients sign in with OAuth 2.1

An MCP client gets an agent token without its person minting one, through the OAuth 2.1
authorization code flow the MCP authorization spec names
([ADR-2048](/architecture/decisions/#adr-2048-an-mcp-client-signs-in-with-oauth-21-for-an-agent-token-linked-to-it)).
Omniglass is both the resource server and the authorization server:

- **Discovery.** `/mcp` answers a request with no token with a challenge naming
  `/.well-known/oauth-protected-resource/mcp`, which names the server's own
  `/.well-known/oauth-authorization-server`.
- **Registration.** `POST /oauth/register` is open dynamic registration of a public client, with
  https or loopback redirect URIs. A client may instead name itself by an https URL serving its
  metadata, fetched through the egress contract and never from a private address
  ([ADR-2074](/architecture/decisions/#adr-2074-an-mcp-client-may-name-itself-by-a-metadata-document-url-fetched-through-egress)).
- **Consent.** `GET /oauth/authorize` (code flow, S256 PKCE, the `/mcp` resource) leads to a console
  consent page where the signed-in person approves roles they cover. An agent token cannot consent.
- **Exchange and refresh.** `POST /oauth/token` spends the five-minute code and mints an agent token
  on the `mcp` channel only, good for an hour, with a refresh token good for 30 days that rotates on
  every use; a spent refresh token presented again ends the grant
  ([ADR-2073](/architecture/decisions/#adr-2073-an-oauth-client-refreshes-a-one-hour-token-with-a-rotating-refresh-token)).

The token is an ordinary agent token from then on.

### The outpost's credential

An outpost is a machine user. An admin mints its enrollment token (`outpost:enroll`), and the
outpost presents it to `POST /outposts:claim`, the one public route that takes a credential in its
body, in exchange for its bus connection details. The embedded NATS server authenticates each
connection in process and grants it publish and subscribe only on that outpost's own subjects, so an
outpost cannot publish or pull as another
([ADR-0036](/architecture/decisions/#adr-0036-a-node-is-a-kindnode-principal-with-an-interim-bearer-credential-and-static-per-connection-nats-subject-permissions)).
What an outpost's batch may write is then held at the gateway: every row lands on the component its
task collects for, under the [writer class](/architecture/storage/#every-key-has-one-writer) its keys
admit.

:::design[A bus credential of its own, tracked in #2616]
Today the enrollment token doubles as the outpost's bus password. The target spends the token at the
claim and issues a distinct bus credential (an nkey with a JWT carrying the outpost's subject
permissions), so a leaked enrollment token cannot be replayed and re-enrolling cuts the old
credential off.
:::

## Roles

A **role** is a named bundle of permissions, which may inherit another role's. Permissions are topic
patterns matched like NATS subjects
([ADR-0015](/architecture/decisions/#adr-0015-permissions-are-topic-patterns-single-token-and-tail-wildcards)):
colon-separated tokens, where `*` matches exactly one token and `>` matches one or more and must be
last.

```
component:read              one permission
component:create,update     expands to two
alarm:acknowledge           a domain verb beside the CRUD verbs
user:*                      any single action on one resource
audit:read:admin            an admin-tier permission, three tokens
>                           everything, at every tier (owner)
```

- **The admin tier is a deeper token.** Because `*` matches one token, `*:read` cannot reach
  `audit:read:admin`. The directories of users, roles and user groups read at this tier
  ([ADR-0023](/architecture/decisions/#adr-0023-the-iam-directory-reads-principal-role-principal_group-are-admin-tier)).
- **Sensitive resources.** A bare `*` never names `secret`, `settings`, `platform` or
  `notification_target`; only a literal grant, a resource wildcard (`secret:*`) or `>` does
  ([ADR-0025](/architecture/decisions/#adr-0025-secret-is-a-sensitive-resource-a-per-secret-admin_sensitive-flag-flips-a-secret-to-the-admin-tier)).
- **The read floor.** Any permission on a resource implies reading it, evaluated in the matcher on
  every call (`rbac.Set.Allows`) rather than expanded ahead.
- **Additive only.** Inheritance composes by union, and there is no negative permission; to narrow,
  define a narrower role.

The five official roles, their inheritance and their **effective** permissions, rendered from
`internal/seed/roles.yaml` through the same `rbac` path the authorizer runs
([#722](https://github.com/hyperscaleav/omniglass/issues/722)):

<SeededSet kind="roles" />

`viewer` reads every operator-facing resource in scope, but no secret and no IAM directory. `operator`
runs the fleet and holds the device secrets in its scope, never an admin-sensitive platform
credential. `deploy` is the integrator's role, usually granted with the `subtree_excl_root` operator
([below](#scopes-and-scope-operators)). `admin` adds `platform:*` and the IAM directories but cannot
grant a role above its own. `owner` is `>`, break-glass, and cannot be impersonated.

A role row carries a namespace (`og` for the shipped five) and an `official` flag. Roles are
read-only today: `GET /roles` (`role:read:admin`) lists them, and the console's role blade shows each
against the permission universe, held versus missing.

:::design[Custom-role management, tracked in #527]
### Custom roles

An admin creates an `official: false` role with a chosen permission set over the IAM API, inheriting
from any role, and edits it on the same blade. An official role inherits only official roles. A
custom role cannot take an official role's name, so `inherits: [viewer]` is never ambiguous.
:::

### The permission universe, published per route

`gated(...)` does three things together: it installs the middleware, stamps the operation with the
`x-omniglass-permission` OpenAPI extension, and records the permission in an in-process catalog. So
the authorization contract is published in the generated `api/openapi.json`, and the **permission
universe** is derived from the routes with no hand-kept list. A route with a second gate stamps it
too: `x-omniglass-platform-permission` for a platform-tier write, and
`x-omniglass-conditional-permission` for one the request's body triggers (a component create naming a
system also needs `system:update`). Three guards keep it honest: every route outside the allow-list
carries a stamp and none on the list does; every permission a seeded role grants resolves into the
universe; and the docs lint fails on a permission named in prose that gates no route.

## Grants: role times scope

A **grant** is a `(role, scope_kind, scope_id, scope_op)` row in `user_grant`, held by a user or by a
user group. A user's grants are **additive**:

```
canDo(P, action, E)  iff  some grant g of P has
                            action in perms(g.role)
                            and E in expand(g.scope)
```

The action and the entity are satisfied by the **same** grant. Flattening every permission into one
set and every scope into another would over-permit: `operator @ room-A` plus `viewer @ all` must not
acknowledge an alarm in room B. So the gateway's set is resolved per action:
`visible_set(P, action)` is the union of the scopes of only the grants whose role carries that action
(`internal/scope`, pure). Reading is the widest set, since every grant carries the read floor, so a
user can read a row it cannot act on, never the reverse.

### Scopes and scope operators

`scope_kind` is `all`, `location`, `system` or `component`, and a scope reaches its root and
everything structurally beneath it. `scope_op` says how the root matches:

| operator | in scope | for |
| --- | --- | --- |
| `subtree` (default) | the root and everything beneath it | every action |
| `subtree_excl_root` | for update and delete, only what is beneath the root | lets a field tech build out a subtree without editing its root |
| `self` | exactly the root row | read, update, delete; never a create beneath it |

Operators combine by union across grants, an inclusive grant winning over an excluding one.

**A location grant reads and creates what is placed in it**
([ADR-1498](/architecture/decisions/#adr-1498-a-location-grant-reads-and-creates-the-systems-and-components-placed-in-it)).
A subtree location grant carrying `system:read` or `component:read` also reaches the systems and
components whose placement is in that subtree, and their create. Every read derived from a
component's scope (its alarms, notifications, dependencies) follows through the same filter.

Each resource registers which grant kinds can contain it (`applicableKinds` in `internal/scope`): a
tier (an alarm, a command or an endpoint on the component tier; pushed telemetry on the component and
system tiers), or fleet-wide, which only an `all` grant confers. `TestEveryGatedResourceRegistersItsScope`
reads every permission stamp in the generated spec and fails on a resource registered nowhere, and the
gateway answers a set resolved for the wrong tier with a wiring error, a 500, never the 404 an empty
grant would earn.

:::design[The cross-tier modify actions and the group scope, tracked in #10]
A location grant also renames, moves and deletes the systems and components placed in it, and a
`group` scope reaches the members of an entity group, recomputed as membership changes. Today the
modify actions stay on their own tier, and the schema refuses a `group` scope.
:::

### Install-wide authority is not fleet scope

The [cascade](/architecture/cascade/)'s least-specific tier is `platform`, the value for the whole
install. A write there needs **two** permissions, the resource's own and `platform:<action>`
([ADR-0057](/architecture/decisions/#adr-0057-the-cascades-least-specific-tier-is-platform-and-a-default-is-not-a-tier)):

```
variable:update + platform:update   change the install-wide value of a variable
secret:create   + platform:create   seal a secret at the platform tier
settings:update + platform:update   every settings write
```

A scope says how much of the fleet a grant reaches; `platform:<action>` says whether the user may
change the value under all of it. `platform` is a sensitive resource, so a custom role with
`*:update` still holds no install-wide authority. Only `admin` is seeded `platform:*`.

### The owner invariant

At least one active `owner @ all` grant exists at all times. A deferred constraint trigger
(`user_grant_owner_guard`) checks it at commit, so swapping owners in one transaction works, and
removing the last one (by revoking, disabling, archiving or purging) is refused with a 409. It is the
one rule the schema holds rather than Go, because only commit time can see two transactions each
revoking the second-to-last owner.

### Grants cannot exceed the granter

A grant is refused (403) unless the granter's own **all-scope** permissions cover the role it confers
(`rbac.Set.Covers`, pattern subsumption)
([ADR-0013](/architecture/decisions/#adr-0013-a-grant-cannot-confer-capabilities-the-granter-lacks)).
No partial wildcard covers `>`, so an admin cannot grant owner, and a capability held only through a
narrower grant cannot be conferred fleet-wide. Users, roles and grants are governed only by all-scope
grants: a scoped admin gets no IAM.

## Enforcement: where each check lives

A targeted write passes three checkpoints, each one code seam:

```d2
direction: down
classes: {
  node: { style.border-radius: 8 }
  group: { style.border-radius: 8 }
}
client: "Client: console / CLI / MCP" { class: node }
api: "API process" {
  class: group
  mw: "Route middleware\ngated(op, 'alarm', 'acknowledge')" { class: node }
  mwq: "action in\nany grant?" { class: node; shape: diamond }
  e403a: "403 permission missing" { class: node }
  handler: "Handler" { class: node }
  mw -> mwq
  mwq -> e403a: "no"
  mwq -> handler: "yes"
}
gwbox: "Storage Gateway" {
  class: group
  gw: "resolve target in visible_set(P, read)\nthen visible_set(P, action)\nwrite and audit_log in one transaction" { class: node }
  e404: "404 non-disclosing" { class: node }
  e403b: "403 readable, not actionable" { class: node }
  db: "Postgres" { class: node; shape: cylinder }
  gw -> e404: "outside read"
  gw -> e403b: "outside action"
  gw -> db: "parameterized predicate"
}
client -> api.mw: "POST .../alarms/X:acknowledge"
api.handler -> gwbox.gw
```

Grants are read from the database on every request; the role index loads once per process, since
roles are read-only today.

### The three-way status split

A refusal picks its status from the difference between two scopes:

| the target is | status | why |
| --- | --- | --- |
| in no grant carrying the action | **403** | the fast reject, before the gateway |
| in `visible_set(P, read)`, outside `visible_set(P, action)` | **403** | the caller can already read this row, so naming the missing authority discloses nothing |
| outside `visible_set(P, read)` | **404** | the caller must not learn the row exists |

One primitive makes the split for every route that has one (`resolveScoped`, and
`ResolveActionTarget` for the routes whose write takes no scope of its own), so the order, read then
action, exists in one place. An action resolves on **its own** permission, never the target entity's
write: acknowledging an alarm resolves on `alarm:acknowledge`, issuing a command on `command:issue`,
pushing telemetry on `telemetry:push`
([ADR-0117](/architecture/decisions/#adr-0117-an-actuation-is-fenced-by-the-permission-that-authorizes-it)).
The read set is always the caller's own `<resource>:read`, because the truthful 403 names a row and
may only reach someone who could have read it.

A **create** has no target yet, so the split is made on the row it is placed under. A location
created under a parent the caller cannot read answers the same 404 as a parent that does not exist
([ADR-1343](/architecture/decisions/#adr-1343-a-location-create-resolves-its-parent-under-read-before-create)).

### A reference resolves within a scope

A location, system or component may be addressed by uuid, bare name or dotted address
([ADR-0089](/architecture/decisions/#adr-0089-a-uuid-is-the-address-a-dotted-path-is-a-positional-lookup)),
and every form goes through one resolver before the decision above: **scope decides before ambiguity
does**. A bare name is narrowed to the caller's scope first, then judged ambiguous only within it, so
an operator scoped to one room can say `display-1` while an unrelated room holds the same name, and an
ambiguity refusal lists only candidates the caller can read. The same rule reaches every resource
whose name is unique only inside something else: an endpoint (`<component>/<name>`), a secret or a
variable (`<owner>/<name>`), a file, a user group and its members
([ADR-1133](/architecture/decisions/#adr-1133-every-operator-resource-answers-to-its-name-and-an-endpoint-is-its-component-and-its-name)).

A bind costs a write on both of its ends. A component created into a system writes that system's
membership, so it needs `system:update`
([ADR-0107](/architecture/decisions/#adr-0107-a-create-that-writes-a-membership-costs-what-the-membership-route-costs));
a membership or slot write naming a component needs `component:update` on it
([ADR-0510](/architecture/decisions/#adr-0510-a-membership-or-a-role-assignment-costs-a-write-on-both-of-its-ends)).

### Resources with no owner

Catalogs, directories and settings describe the install, not the fleet, so they carry no owner to
scope by:

- **Users, roles and grants**: the action must be in an all-scope grant.
- **Catalogs** (the metric, property, event and command types, tags, products, standards): each its
  own resource with its own verbs (`property_type:create`, `standard:update`), so a curator role mints
  entries without IAM. A shipped row is forked, never written
  ([storage](/architecture/storage/#conventions)).
- **Settings**: the permission alone gates them, a recorded carve-out
  ([ADR-0034](/architecture/decisions/#adr-0034-the-settings-gateway-is-unscoped-only-the-permission-gates-it),
  [settings](/architecture/settings/)).

### Coverage grows with the surface, by test

- An **authorization conformance matrix** runs the full set (the 403 on a missing permission, the
  over-permit 403, the non-disclosing 404, in-scope success) against every scoped entity in a
  catalog, and through each route that hangs off one. A new scoped entity is one catalog line.
- `TestEveryRouteIsGated` holds the route invariant above. Its allow-list is the public routes (the
  liveness probe, sign-in and its status, the outpost claim, and the webhook receiver, whose token
  names one endpoint and whose driver's scheme authenticates the sender,
  [ADR-1024](/architecture/decisions/#adr-1024-omniglass-receives-webhooks-on-the-server-and-a-webhook-token-is-a-sealed-secret))
  and the self-scoped `/auth/me` family and `GET /settings/me`, which act only on the caller.

## User groups

A **user group** is a set of users that holds grants. Every member inherits the group's grants
through the same loader as their own, and a group grant is bounded by the same cover check as a
direct one. Membership is static and flat, and each row carries a `source` (`local`, or `idp` with its
issuer when synced from a provider's groups claim). The `/user-groups` routes manage groups, members and
grants, gated on `user_group`.

### People as notification audiences

A user group, a person or a role is also an **audience** for alarm notifications
([alarms and actions](/architecture/alarms-actions/#people-group-and-person-targets-and-the-inbox)).
The scope invariant holds for what a person is told, not only what they query: each member is told
only when their own component read scope admits the alarm's component, judged at the transition and
again when they read their inbox, so a revoked grant empties the entry at once
([ADR-1341](/architecture/decisions/#adr-1341-a-person-is-told-about-an-alarm-only-while-they-can-read-it-groups-expand-at-queue-time-scope-is-checked-there-and-again-at-delivery)).
A person subscribes themselves with `notification:subscribe`, which `viewer` carries.

## Impersonation

An owner or all-scope admin holding `user:impersonate` can see or act through another user, for
troubleshooting. **View-as** resolves reads under the target's scope and refuses every write;
**act-as** is full, and every write records both the target and the real actor.
`POST /users/{id}:impersonate` mints a bounded token (30 minutes by default) held in
`impersonation_session`, apart from credentials. An owner cannot be impersonated by anyone, a caller
may impersonate only a user whose permissions its own cover, and act-as needs the caller's all-scope
grants alone to cover the target. Disabling either party ends the session at its next request.

## Sessions and the self-service surface

`GET /auth/me` returns the caller, their grants, and the flat union of their roles' raw patterns.
The console uses the patterns only to hide or explain (a button the caller could never use, a page
they cannot read, which renders a denied face naming the permission); the server's check on every
route is the control.

The `/auth/me` family acts only on the caller: editing their profile, changing their password,
listing and revoking their own sessions and tokens (keeping the one making the request), and minting
a token. The admin counterparts act on another user and carry permissions:
`user:reset-password`, `user:revoke-session`, `user:set-avatar`. A reset and a session revoke sit
behind the **takeover guard**: nobody can do either to an owner, or to a user whose permissions exceed
their own.

A user's lifecycle is reversible until the end: `:disable` and `:enable`; `:archive` and `:restore`,
which hide the account and block sign-in; and `:purge`, which deletes it, needs prior archival and
`user:purge:admin`, and keeps the audit trail by the actor's name copied onto each row.

A profile picture is normalized on the server (JPEG, PNG or WebP in, at most 8 MiB and 8000 pixels a
side, cropped and re-encoded to a 256 pixel square JPEG) and read back as JSON, not raw bytes, so its
route stays behind the same middleware as every other
([ADR-0018](/architecture/decisions/#adr-0018-the-avatar-read-endpoint-is-json-not-raw-image-bytes)).

## Bootstrap and break-glass

`omniglass bootstrap <username>` creates the first owner in one transaction, with an `owner @ all`
grant and a token, and with `--password` a password for the console. There is no default user. Two
direct-database commands are the recovery path and skip the password policy, since they already need
database access: `bootstrap`, and `omniglass set-password`, which also revokes the person's sessions
and, with `--revoke-tokens`, their tokens. It is the one way to cut off a compromised owner, since
every API reset and revoke refuses an owner target.
