Core entities are the things an operator manages, component, system, location, and node, each with
its own identity so that every sample, event, alarm, and config names exactly one owner. The shapes
they pin are [templates](/architecture/templates/); the data they own is
[samples](/architecture/properties/); the physical tables are [storage](/architecture/storage/).

:::note[Partial]
Built today: `component`, `system`, and `location` as name-addressable, variable-depth (`parent_id`)
trees with full scoped CRUD; a delete is refused while a structural child remains. **Placement and
classification are mutable, not fixed at create** ([ADR-0064](/architecture/decisions/#adr-0064-placement-and-classification-are-mutable-after-create)):
re-parent (cycle-guarded), relocate, re-classify, or clear each field; a product swap keeps hand-set
property values while the new contract's defaults take over. Each entity carries an **optional
classifier** (`product` / `standard` / `location_type`; the `component_type` registry retired,
[ADR-0047](/architecture/decisions/#adr-0047-the-fields-fold-product_property-and-property_value);
`system_type` was promoted to `standard`,
[ADR-0048](/architecture/decisions/#adr-0048-the-standard-blueprint-and-the-template-fork-seed-model)).
The **exclusive-arc** owner columns are real, carrying the sample sinks, **`event`**, **`property`**,
and a recorded **[health](/architecture/health/)** series per component, system, and location. A
system declares **roles** staffed by components whose **resolved capabilities** cover them, each role
carrying an **impact**. See [implementation status](/architecture/status/).
:::

## The estate: four structural entities

- A **component** is a deployed device, app, or service (a display, a DSP, a cloud UCC service). It
  owns samples and points at the **`product`** it is, the source of its shape; the pointer is
  optional, so a productless component carries no contract.
- A **system** is a set of components doing one job: a meeting room, a classroom, a video wall. It is
  located at a location and **conforms to a `standard`**, the blueprint it is built against; the
  pointer is optional, mirroring `component.product_id`.
- A **location** ties systems and components to a physical place, classified by `location_type`, its
  only shape-definer (no template). A starter type set ships seeded, operator-owned
  ([the seed model](#the-seed-model-forked-templates-versus-canonical-catalogs)), read at
  `GET /location-types` to feed the location form's type picker. Each type carries an `icon` (a glyph
  key like `building`; unknown keys fall back to `map-pin`) rendered in the tree, and
  `allowed_parent_types` (a set of `location_type` ids and/or the reserved `root` sentinel): empty is
  unconstrained, a non-empty set is enforced on create and move, seeded as `campus={root}`,
  `building={root,campus}`, `floor={building,campus}`, `room={floor,building,campus}`.
- A **node** is the edge process (`omniglass node run`) that pulls work, reaches components over
  interfaces, and ships results ([nodes](/architecture/nodes/)). It is structural because it is a
  first-class **owner** of its own self-health telemetry and node-owned alarms.

```d2
direction: down
classes: { node: { style.border-radius: 8 }; key: { style: { border-radius: 8; bold: true } } }
location: location { class: node }
system: system { class: key }
c1: component { class: node }
c2: component { class: node }
c3: component { class: node }
location -> system
system -> c1
system -> c2
system -> c3
```

:::design[The `global` estate owner (ADR-0057)]
Above the four sits a singleton **`global`** estate owner where estate-wide health and KPIs roll up:
one per deployment, no FK, no built table carrying a `global` arm today (every arc CHECK admits
exactly `component | system | location | node`). An **owner** only: not a location (the location tree
is a forest of N unparented tops, no root) and not the [cascade](/architecture/cascade/)'s
least-specific tier, **`platform`**
([ADR-0057](/architecture/decisions/#adr-0057-the-cascades-least-specific-tier-is-platform-and-a-default-is-not-a-tier)).
:::

| Entity | What it is |
|---|---|
| `component` | a deployed instance (`dsp-boardroom-3`); points at its `product`, the source of its shape |
| `system` | a composition of components / subsystems (the service tree); conforms to its `standard` |
| `location` | a place tree; no template (the `location_type` is the only shape-definer) |
| `node` | the edge process; its name is the identity, bound to a credential ([identity and access](/architecture/identity-access/)) |

### Catalog reference data: vendor, driver, capability

The **component-classification catalogs** are flat, seed-and-custom registries on the same
official/custom pattern as the `*_type` registries ([Types guide](/guides/admin/types/)); the
**`product`** catalog (below) sits above them as the concrete SKU a `component` points at:

- A **`vendor`** (Crestron, Biamp, ...) names an organization, with a **`kind`** of `manufacturer`,
  `integrator`, or `developer` (default `manufacturer`); the generalization of the former
  manufacturer-only `component_make`.
- A **`driver`** (Generic SNMP, Cisco xAPI, ...) names the implementation that gets, emits, or sets a
  product's signals, with an optional **`version`**.
- A **`capability`** (Microphone, Display, ...) names what a component can do, claimed by a
  **product** (the default for its instances) and by a **component** (its own facts, layered over the
  product's); it is what a [system role](#system-roles-the-slots-a-system-needs-filled) requires.

See the [Vendors guide](/guides/admin/vendors/) for the operator surface.

### Catalog reference data: `product`

A **`product`** (Cisco Room Bar, Samsung QM55, ...) is the concrete **SKU**: a stable `id` and
`display_name`, a **`kind`** (`device` / `app` / `service` / `vm`, default `device`, a fixed enum
checked in the DB and at the API edge), optional **`vendor_id`** and **`driver_id`**, an optional
**`parent_product_id`** (a variant points at its base), and the `official` boolean. Its capabilities
live in the **`product_capability`** join (`product_id`, `capability_id`). The vendor, driver, and
parent FKs are **`on delete set null`**.

A **`component`** points at the product it **is** through **`component.product_id`**
(**`on delete restrict`**): the referential guard the leaf catalogs deferred, so a product still
referenced by a component cannot be deleted (409). See the [Products guide](/guides/admin/products/).

### Catalog reference data: `standard`

A **`standard`** (Huddle Room, Classroom, ...) is the **blueprint a system conforms to**: a stable
`id` and `display_name`, an optional **`parent_standard_id`** (a variant points at its base), and
the `official` boolean; the promotion of the former `system_type` label registry
([ADR-0048](/architecture/decisions/#adr-0048-the-standard-blueprint-and-the-template-fork-seed-model)).

A **`system`** conforms through the optional **`system.standard_id`**; a **one-off system** is
first-class and carries no contract. Conformance is **not** a copy: the standard's contract defaults
resolve **live** for every conforming system until it overrides one. See the
[Standards guide](/guides/admin/standards/).

### Declared properties: the classifier contracts and the value store

A classifier also **declares what its instances expose**, in three tables of one shape:
**`product_property`**, **`standard_property`**, and **`location_type_property`**, one row per
declared property (`<classifier>_id`, a **`property_type_id`** FK into the
[`property_type` catalog](/architecture/variables/), an optional `default_value` in jsonb, a
`required` flag), unique per `(classifier, property)`; the API body carries `property_type_name`,
resolved to the FK at the edge. Type and validation live on the property, never repeated here.

The value lives in **`property`**, on the **same owner exclusive-arc** as the sample sinks and
`event` ([below](#ownership-the-exclusive-arc)), plus the **`property_type_id`** FK, an `instance`
discriminator, a **`provenance`**, and the jsonb `value`. Provenance makes the fold work: one table holds values an operator **declared**, a device
**observed**, a rule **calculated**, and config **intended**; the per-provenance producers are on
[config, secrets, and variables](/architecture/variables/#property-one-typed-name-a-classifier-contract-a-stored-value).

The read is **`EffectiveProperties(ownerKind, ownerID)`**, one query with two arms: the **contract
arm** (every property the classifier declares, resolved to
`coalesce(the instance's declared value, the contract default)`, marked `from_contract`) and the
**off-contract arm** (values set directly on the instance); an instance with no classifier set (a
**productless** component, a **one-off** system) resolves to its off-contract arm alone, and a
**node**, with no classifier, always does.

**One resolver serves all four owner kinds.** The pairs differ only in five identifiers (instance
table, classifier column, contract table, contract key, arc column), held as data in an
`ownerContract` table, so the SQL is written **once**, the primitive-first move
([ADR-0048](/architecture/decisions/#adr-0048-the-standard-blueprint-and-the-template-fork-seed-model)):

| Owner kind | Classifier column | Contract table |
|---|---|---|
| `component` | `component.product_id` | `product_property` |
| `system` | `system.standard_id` | `standard_property` |
| `location` | `location.location_type` | `location_type_property` |
| `node` | (none) | (none) |

Every arc is **scope-checked on the write**: setting a value outside your scope is a non-disclosing
404.

This pair replaces the retired `field_definition` / `field_value` feature: a "field" was always a
property with **declared** provenance
([ADR-0047](/architecture/decisions/#adr-0047-the-fields-fold-product_property-and-property_value)).
See the [Properties guide](/guides/admin/properties/).

### System roles: the slots a system needs filled

A contract says what a system **carries**; a **system role** says what it **needs filled**: a table
microphone, a main display. A role is a **slot**, not a component, so an **unfilled slot is visible**
rather than absent.

:::note[Not the IAM role]
A **system role** is a slot in a system; an **[IAM role](/architecture/identity-access/)**
(viewer / operator / admin / owner) is a capability set granted to a principal. They share only the
word: the storage methods are `ListSystemRoles` / `SetSystemRole` / `DeleteSystemRole`, not
RBAC's `ListRoles` / `UpsertRole`.
:::

Five tables carry it. `system_member` is the **membership** binding a role attaches to, many-valued
and cascading from both ends; `system_role` is the slot, on the same arc `property` uses
(one-set CHECK, `unique nulls not distinct` over the arc plus name); `system_role_capability` is
what the role requires, **conjunctive** (a component must provide **every** listed capability);
`component_capability` is the component's **own** capability facts, layered over its product's; and
`system_role_assignment` is who fills the role here.

### Membership: what a role attaches to

**A component doing a job in a system is a member of it, and the role is what that membership does**:
one attachment seen at two levels. Membership is **many-valued** (a rack DSP feeding three rooms is a
member of all three). **Staffing a role creates the membership**, so nobody says it twice; the
reverse is not symmetric: giving up a role does not end membership, and a member carrying no role is
ordinary (the spare on the shelf).

**`is_primary`** marks which membership seeds the
[cascade](/architecture/cascade/#structural-multi-membership-a-component-in-n-systems) for a caller
*without a system in hand*: a default, never a rule overriding a caller who named a system. The
first membership takes it automatically; a partial unique index forbids a second primary.

Membership **cascades from both ends**, and does not restrict the component the way
`system_role_assignment` does: that restrict is load-bearing (deleting a filler would silently break
health); a role-less membership is not worth blocking a delete over.

**A role is declared on a standard or on a system**, the same exclusive arc the value store uses:
standard-declared roles are **inherited live** by every conforming system, like a contract default;
system-declared ones are ad-hoc, how a one-off system gets roles and a conforming system adds beyond
its standard. A role carries a **`quorum`** (two ceiling mics is one role with quorum 2), at least
one.

**A capability is a fact about a component, not only its product.** `component_capability` layers
over the product's set: `present=true` adds a capability the product does not claim, `present=false`
suppresses one it does. The resolver **`EffectiveCapabilities(component)`** is:

> the **product's** capabilities, UNION the component's **`present=true`** rows, MINUS its **`present=false`**
> rows.

A **productless** component resolves to just its own declarations: the platform's single definition
of "what this component can do".

The read side is **`EffectiveRoles(system)`**: the standard's roles (marked `from_standard`) UNION
those declared directly, each with its required capabilities, quorum, and fillers **here**, serving
**assigned** and **understaffed** (quorum minus assignments, floored at zero) so every surface reads
the same.

**Assignment is refused when the component cannot fill the role**, with the missing capabilities **named**:

```
component "panel-1" cannot fill role "table-mic": missing microphone, speaker
```

A refusal on **modeled** grounds. It is also why capabilities are a **resolved** set: `product` is
optional, so a product-only guard would lock every productless component out of every role
([ADR-0049](/architecture/decisions/#adr-0049-the-system-role-capability-gated-staffing-and-the-resolved-capability-set)).

**A role also declares its `impact`**: `outage`, `degraded`, or `none`, what an **impaired** role
(fewer satisfying components than quorum) means for its system. It lives on the role because the same
broken box matters differently per slot: a dead confidence monitor is not a dead main display. Impact
is the one input [health](/architecture/health/) takes from the declaration side; **quorum is the
redundancy knob** beneath it. Staffing stays readable **without** health (a role wanting two with one
assigned is under-staffed today); health adds whether the assigned components can currently do the job
([ADR-0050](/architecture/decisions/#adr-0050-health-is-a-recorded-transition-computed-from-the-alarm-capability-role-chain)).

### The seed model: forked templates versus canonical catalogs

Shipped content is two kinds, never conflated:

- **Example content** (a `standard`, a `location_type`) is created by **forking an in-code template**
  ([#317](https://github.com/hyperscaleav/omniglass/issues/317); shipped boot seeds stand in today).
  The fork is **one-time, no inheritance**: nothing points back at the template, so it can improve
  per release without touching a tenant. What lands is an **operator-owned** row (`official: false`),
  installed **only if absent** (`ON CONFLICT DO NOTHING`) so re-seeding never reverts an edit; a
  shipped standard's **roles** ride the same lane.
- **Canonical vocabulary** (the [`property_type` catalog](/architecture/variables/), the `event_type`
  and `command_type` registries) is the shared namespace a driver maps onto, identical install to
  install: seeded `official: true` through an **authoritative upsert** (`ON CONFLICT DO UPDATE`),
  read-only in the API. The classification catalogs (`vendor`, `driver`, `capability`, `product`)
  ride that path today.

**Forking applies to template -> row, never to classifier -> instance**: a system conforms, never
forks.

## The variable-depth trees

`component`, `system`, and `location` are each a **variable-depth tree**: a `parent_id`
self-reference nesting to arbitrary depth (campus -> building -> floor -> room). The trees are the
structural backbone of the [cascade](/architecture/cascade/), which resolves over an entity's
containment path; precedence is stated once, there.

```d2
direction: right
classes: { node: { style.border-radius: 8 }; key: { style: { border-radius: 8; bold: true } } }
component: component { class: node }
product: product { class: node }
location: location { class: node }
system: system { class: node }
standard: standard { class: node }
component -> product: is a (N:1)
component -> component: parent (tree)
system -> standard: conforms to (N:1)
system -> location: located at (N:1)
system -> system: parent (tree)
location -> location: parent (tree)
```

### Sub-components and sub-systems

The `parent_id` self-reference is **same-kind nesting**: a chassis with line cards is a parent
component over children, and likewise a parent system over room subsystems. The nesting feeds the
[cascade](/architecture/cascade/) (deeper wins) and the **health rollup** (sub-system into parent
system, sub-component into parent component, [health](/architecture/health/)). The **practical
starting depth is 3 levels**, **not a hard cap**.

## Ownership: the exclusive-arc

Everything observed, asserted, or set attaches to exactly one structural entity through the
**exclusive-arc**. Every sample table, plus `event`, `property`, `alarm`, and `variable`, carries:

- an **`owner_kind`** enum, plus
- the **matching typed FK** (`component_id` / `system_id` / `location_id` / `node_id`), plus
- a **CHECK** that exactly the column matching `owner_kind` is set.

Every built CHECK admits exactly `component | system | location | node`.

:::design[The `global` all-null arm (ADR-0057)]
The singleton `global` owner rides the same arc as an all-null arm: none of the four owner columns set.
:::

This makes **system-, location-, and node-level samples first-class** (`health` is a `state` owned by
a system; a node's self-health is owned by the node); estate-wide samples owned by `global` are the
designed extension. The **owner** gives a recorded [health](/architecture/health/) verdict its level:
component, system, and location each own a transition series under the same `health` key. The same
arc owns the `event` rows a sample produces, and is the design for `alarm` (component-local today),
so a system-owned sample will yield a system-owned alarm. The full pattern and DDL are on
[storage](/architecture/storage/).

### The event sink: the first arc-owned occurrence

The arc's first built sink beyond the sample tables is **`event`**, the **occurrence sink**: a
**past occurrence** with no "what is it now?", against a `metric` or `state`'s sampled present value
(the [has-a-value-now razor](/architecture/properties/#the-has-a-value-now-razor-sample-vs-event)).

An `event` row carries the **identical owner exclusive-arc** as a sample (same one-set CHECK) and
the **same provenance** vocabulary (`observed` / `calculated` / `intended` / `declared`, default
`observed`), so the same owner-confinement and reject-not-project gates apply at ingest. The occurrence key
(`event_type_id`), the lineage columns, and the separate raw `log_line` lane
([ADR-0066](/architecture/decisions/#adr-0066-logs-are-a-raw-ingest-lane-not-events)) are the
[events](/architecture/events/) page's model. Closing the loop, the reserved **`event_id`** columns
on `metric` and `state` are now **real foreign keys** to `event(id)` (`on delete set null`): an
**intended**-provenance sample references the `event` that produced it
([samples](/architecture/properties/)).

## Operational mode: active, maintenance, disabled

Every entity has an **operational mode**, cascade-resolved (set on the entity or inherited,
[cascade](/architecture/cascade/)):

- **active** (default): collect, evaluate, act, enforce drift, count toward SLA.
- **maintenance**: **keep collecting**, but **suppress the consequences**.
- **disabled**: **stop collecting and interacting** entirely (the Zabbix host-disable); dormant until
  re-enabled.

Maintenance and disabled are the **same suppression**, differing only on the **collection** knob. Both
suppress four consequences:

- **action dispatch is held**: an alarm may open, but no `action_rule` pages or opens a ticket
  ([alarms and actions](/architecture/alarms-actions/));
- **drift is observed, not enforced**: the set function never fires, so a tech mid-swap is not fought
  ([config](/architecture/variables/));
- **health rolls up no impact**: the member does not sink its parent's
  [health](/architecture/health/); it surfaces as "outage (maintenance)", the truth plus the mode;
- **SLA does not count it**: the window is excluded from availability and the SLO.

Maintenance is **time-bound**: a window (start / end, [time](/architecture/time/)) that
**auto-exits**, or open-ended until cleared, recurring as a schedule; disabled holds until re-enabled.
Either transition is **audited** ([audit](/architecture/audit/)), so "no page at 2am, it was in the
patch window" is explainable. Cascade resolution means maintenance on a system covers its components.
:::

:::design[Decommission, purge, and the delete cascade, tracked in #528]

## Decommission and delete

"Delete" is **decommission** by default, a **soft delete**: tombstoned, out of placement, worklists,
and default views, with **history retained** (samples, events, alarms, audit) and aging out by
[retention](/architecture/storage/); re-commissionable. **Purge** is the privileged, audited hard
erase for a genuine mistake, a background job over the partitions for a high-volume entity.

Decommissioning runs the **in-flight cleanup** with existing mechanisms: collection stops, **open
alarms auto-resolve** (reason "decommissioned"), **pending commands and running flows cancel**, and
config / tag / credential / group bindings drop. The entity leaves its parent's health rollup.

The cascade is **not** "delete everything below", because containers do not own their members:

- a **component** (leaf) decommissions as above;
- a **system** delete **unbinds its members** (the `system_member` rows) but keeps the components,
  standalone and re-homeable;
- a **location** delete is **refused by the API while occupied**; today the occupancy check counts
  only child locations (`parent_id` children), a still-placed system or component surfacing as the
  generic referenced error; the console offers re-homing first;
- a **node** delete **re-places its tasks** (to the server or another node, or surfaces the
  components as uncollected) and revokes the node credential
  ([identity and access](/architecture/identity-access/)); `node.*` history is retained.

:::

## How an entity is identified

Three things, and no fourth:

- **id**, a uuid. Immutable, the primary key, and what every foreign key stores, so a rename has
  nothing to rewrite.
- **key**, the machine identifier an operator types and a URL, a CLI argument, and a topic carry.
  Mutable, which is the point: `cisco-room-bar` is a typo or a rebrand away from being wrong forever
  if it cannot change.
- **name**, an optional free-text label. Absent is normal: `crestron` needs no label, and a tag never
  has one.

Every exception is declared in `internal/storage/identity_shape.go` and rendered below, so this page
cannot drift from the code. Most tables are key-bearing and the shape explains itself. The two that
need a reason are the ones where an identifier exists but is not a key.

A **keyspace** table carries a key on the other key rule (that same kebab segment, optionally
dot-hierarchied). The two rules stay two rules because only a keyspace key may carry the dot, but
they are one validator: `storage.ValidateName` picks between them from the table's declared shape,
so a call site cannot pick wrongly or forget to pick at all. The console still says Key for both,
and that one difference surfaces as a validation message rather than as a second word.

Everything else is **id-only**: a join row and a telemetry row are addressed by uuid because nobody
names them. An operator names the component, not the metric.
