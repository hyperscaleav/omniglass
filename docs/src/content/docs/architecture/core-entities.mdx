The **fleet** is everything an install manages: the locations, the systems in them, and the
components that make them up, with the outposts that reach them. Each is a row with its own
identity, so every sample, event, alarm, command and config value names exactly one owner. To work
with them in the console, see [entities](/operator/entities/); the full relational shape is the
[data model](/architecture/data-model/).

## The fleet: four structural entities

- A **component** is one managed device, app or service (a display, a DSP, a cloud calling
  service). It is an instance of a **product**, and the pointer is required: three shipped generic
  products (`generic-device`, `generic-app`, `generic-service`) cover anything not modeled more
  specifically.
- A **system** is a set of components doing one job (a meeting room, a classroom, a video wall). It
  is the unit Omniglass monitors and the one support troubleshoots through, with one
  [health](/architecture/health/) of its own. It may conform to a **standard** and be classified by
  a **system type**, both optional.
- A **location** is where things sit, from a campus down to a room, in the customer's own tree. A
  location's **location type** is required, and is the only thing that shapes it.
- An **outpost** is the collection process (`omniglass outpost run`) that runs tasks and commands
  over endpoints and reports back ([outposts](/architecture/outposts/)). It is structural because
  it owns its own telemetry and alarms.

A system is the logical grouping the business cares about; a location is the physical one. Where a
location holds exactly one system the two coincide, and the console shows them as one detail view
([ADR-0139](/architecture/decisions/#adr-0139-a-detail-view-is-one-per-system-its-place-a-card-of-context)).
A component joins a system through membership ([below](#membership-what-a-slot-attaches-to)), and
may also carry a location of its own.

::::design[Target design: every system has a location and bounds its components (ADR-0140), tracked in #876, #877, #878 and #879]
Today a system's location is optional, a component's location is only what was explicitly set, and
system nesting exists in storage with no console surface.
[ADR-0140](/architecture/decisions/#adr-0140-a-system-is-what-the-business-groups-a-location-is-where-things-sit-and-a-room-is-one-thing)
settles the model:

- **Every system has a location** ([#876](https://github.com/hyperscaleav/omniglass/issues/876)),
  the deepest one spanning everything it needs; a system with none backfills to the deepest
  location containing its members.
- **A system's location bounds its components and subsystems**
  ([#877](https://github.com/hyperscaleav/omniglass/issues/877)): a component's own location sits at
  or below its primary system's, and a move that would strand one is refused, naming it.
- **A component inherits its primary system's location unless set**
  ([#878](https://github.com/hyperscaleav/omniglass/issues/878)), derived at read time, so moving a
  system carries its components with it.
- **Systems group into systems** ([#879](https://github.com/hyperscaleav/omniglass/issues/879)): a
  divisible hall is one system holding the shared head-end, with a subsystem per room.
::::

## The catalogs that classify the fleet

A **catalog** row is something the fleet is typed by. Every catalog shares one pattern: shipped rows
(`official`, namespace `og`) that the boot seed writes and a release may improve, beside an
admin's own rows (namespace `local`). The classifiers are:

| Classifies | Catalog | Nests | Admin page |
|---|---|---|---|
| a product | `component_type` | yes, by `parent_id` | [products](/admin/products/) |
| a component | `product` (with `vendor` and `driver`) | a variant points at its base | [products](/admin/products/) |
| a system, by purpose | `system_type` | yes, by `parent_id` | [standards](/admin/standards/) |
| a system, by contract | `standard` | a variant points at its base | [standards](/admin/standards/) |
| a location | `location_type` | no; `allowed_parent_types` constrains the tree | [location types](/admin/location-types/) |

### Catalog reference data: vendor, driver

A **vendor** is an organization behind products, of kind `manufacturer`, `integrator` or
`developer`. A **driver** is the declared recipe that collects from a product and sets its signals
([collection](/architecture/collection/)); a product names at most one.

### Catalog reference data: `component_type`

A **component type** is the device class a product belongs to (`display`, `projector`, `dsp`,
`mic`). It nests: category roots, subcategories and leaves, after the OpenAVCloud AV Device Taxonomy
([ADR-0131](/architecture/decisions/#adr-0131-the-device-taxonomy-is-oavc-and-the-demo-catalog-is-fictional)).
It classifies the **product**, never the component directly
([ADR-0085](/architecture/decisions/#adr-0085-the-component_type-registry-returns-as-the-device-class-genus)),
so a component's type is read through `component.product_id -> product.component_type_id`.

A type carries the identity facts that span its products, each **inherited down the tree** and
shadowable at any level: the naming `stem`, `label`, `icon`, the short `abbrev`, a `label_rule` and
`default_tags`. A blank fact means "inherit the nearest ancestor's"; patching a fact to `""` puts it
back to inheriting. A root must state its own stem. The catalog listing serves each row's resolved
icon and what it would inherit, with the ancestor each fact comes from, in one statement however
deep the tree runs, so no client re-implements the walk. A subtype exists only where a standard's
slot would name it: `wireless-mic` beside `ceiling-mic`, never `lcd` beside `led`.

### Catalog reference data: `product`

A **product** is a concrete model a vendor sells: a required `kind` (`device`, `app` or `service`,
no default), a required `component_type_id` (on delete restrict), and optional `vendor_id`,
`driver_id`, `parent_product_id` (a variant), `icon` override and `label_rule`. A product still
referenced by a component cannot be deleted (409).

### Catalog reference data: `system_type`

A **system type** says what a system is for (meeting, teaching, signage), never the space it sits
in ([ADR-0096](/architecture/decisions/#adr-0096-the-system_type-name-returns-as-the-coarse-space-taxonomy)).
It nests like `component_type` and carries the same inherited `stem`, `label`, `icon`, `abbrev` and
`label_rule`, without `default_tags`. A type still classifying a system or parenting another type
cannot be deleted.

<SeededSet kind="system_types" />

### Catalog reference data: `standard`

A **standard** is the contract a system is built to: the slots it fills and the properties and
metrics every conforming system exposes. Type and standard are separate axes: one fleet can hold
ten signage standards under a single signage type, and a one-off system carries neither. A
conforming system reads the standard's slots and defaults **live**, never a copy.

### Declared properties: the classifier contracts and the declared rows

A classifier also declares what its instances expose. `product_property`, `standard_property` and
`location_type_property` each bind a [property type](/architecture/properties/#the-two-catalogs)
with an optional `default_value` and a `required` flag; `product_metric`, `standard_metric` and
`location_type_metric` do the same for metric types. An operator's value is a `declared` row in the
property series itself
([ADR-0079](/architecture/decisions/#adr-0079-five-telemetry-lanes-and-property-stops-being-the-genus)),
so an edit appends and the history is the series.

One read, `EffectiveProperties(ownerKind, ownerID)`, serves every owner kind. It returns each
contract property as `coalesce(the owner's latest declared value, the contract default)`, plus any
value set on the owner off contract. A component with a generic product, a one-off system, or an
outpost (which has no classifier) resolves its off-contract values alone. The pairs differ only in
five identifiers held as data, so the SQL is written once:

| Owner kind | Classifier column | Contract table |
|---|---|---|
| `component` | `component.product_id` | `product_property` |
| `system` | `system.standard_id` | `standard_property` |
| `location` | `location.location_type` | `location_type_property` |
| `outpost` | none | none |

A write outside the caller's scope is a non-disclosing 404. To declare a contract, see the
[properties admin page](/admin/properties/).

### System slots: what a system needs filled

A **system slot** is a position in a system a component fills: a main display, a table microphone.
A slot is a position, not a component, so an unfilled slot is visible rather than absent. A slot is
declared on a standard (every conforming system inherits it live) or on one system (how a one-off
system gets any, or a conforming one adds more). Each carries:

- a **quorum**, how many fillers it wants (two ceiling mics is one slot with quorum 2), and an
  optional **capacity** at or above it;
- an **impact**, `outage`, `degraded` or `none`: what the slot being impaired means for its system's
  [health](/architecture/health/). It lives on the slot because the same broken box matters
  differently per slot;
- a **typed-slot guard**: the component types a filler's product must fall within (self or a
  descendant; none listed accepts any), and optionally the exact products it may be.

A standard can also state **choices**: an exclusive-or group of alternates (an all-in-one video bar,
or a component-built kit), each slot joining one alternate. Health folds only the best-satisfied
alternate's slots, so the unbuilt alternate never takes the room down.

A slot name means one slot in a system: a system declaring a name its standard already declares is
refused with a 409, never shadowed
([ADR-0503](/architecture/decisions/#adr-0503-a-role-name-addresses-one-role-per-system)).
Assignment is refused when the component cannot fill the slot, naming both parties:

```
component "panel-1" is a display; slot "table-mic" wants a video-bar
```

Changing a system's standard carries each occupant onto the new standard's slot of the same name
when it still fits, and releases the rest (they keep their membership), in one audited transaction
([ADR-0506](/architecture/decisions/#adr-0506-changing-a-systems-standard-carries-its-staffing-onto-the-roles-that-still-exist)).
`EffectiveSlots(system)` is the one read: the standard's slots and the system's own, each with its
guard, quorum, fillers and how understaffed it is.

### Membership: what a slot attaches to

A component doing a job in a system is a **member** of it (`system_member`), and a slot is what that
membership does. Membership is many-valued: a rack DSP feeding three rooms is a member of all three.
Filling a slot creates the membership; giving the slot up does not end it, and a member with no slot
is ordinary. `is_primary` marks the one membership that seeds the
[cascade](/architecture/cascade/#structural-multi-membership-a-component-in-n-systems) for a caller
with no system in hand; the first membership takes it, and a partial unique index forbids a second.

A membership writes onto both its ends, so binding, unbinding, re-defaulting or staffing costs
`system:update` on the system and `component:update` on the component
([ADR-0510](/architecture/decisions/#adr-0510-a-membership-or-a-role-assignment-costs-a-write-on-both-of-its-ends)).
A component create that names a system writes the same row, so it costs the same
([ADR-0107](/architecture/decisions/#adr-0107-a-create-that-writes-a-membership-costs-what-the-membership-route-costs)).
Membership is its own verb (`/systems/{name}/members`, `:setPrimary`), never a field on the
component's update.

### The seed model: templates versus canonical catalogs

Shipped content comes in two kinds, never conflated:

- **Example content** is created from a [template](/architecture/templates/)
  (`POST /standards:createFromTemplate` and its siblings). The copy is one-time with no link back:
  what lands is an operator-owned row, audited once as a create carrying `from_template`. The boot
  seed plants no standard
  ([ADR-0827](/architecture/decisions/#adr-0827-the-template-layer-owns-the-clone-model-and-the-componenttemplate-authoring-model-is-superseded-by-the-driver-spec)).
- **Canonical vocabulary** (the metric, property, event and command type catalogs, and the
  classification catalogs `vendor`, `driver`, `component_type`, `product`, `system_type` and
  `location_type`) is the shared namespace a driver maps onto, identical install to install. The
  boot seed writes it with an authoritative upsert on every start, as `og` rows an operator never
  writes
  ([ADR-0106](/architecture/decisions/#adr-0106-a-location-type-is-platform-owned-and-a-nullable-object-clears-under-the-mask)).

Copying applies from template to row, never from classifier to instance: a system conforms, it
never copies.

An admin who wants a shipped row to read differently **forks** it
([ADR-0095](/architecture/decisions/#adr-0095-an-operator-forks-a-shipped-registry-row-instead-of-the-platform-writing-it)).
The edit stores the admin's version of the row's mutable facts in `catalog_shadow`, keyed on the
shipped row's uuid, and every read resolves the shadow over it. The shipped row is never written, so
the next release can still improve it, and `:restore` (on component types and location types)
discards the shadow. A fork restates facts, never structure: the uuid, name, `official` flag and
parent stay shipped, so foreign keys, tree walks and URLs keep naming the same row. The console
reads three origins: official, custom, and overridden.

## The variable-depth trees

`component`, `system` and `location` each nest by a `parent_id` self-reference to any depth
(campus, building, floor, room). The trees are what the [cascade](/architecture/cascade/) resolves
over. A move re-parents through the `:move` custom method, guarded against cycles
([ADR-0088](/architecture/decisions/#adr-0088-a-placement-change-is-an-authorization-act-so-a-move-is-its-own-verb)):
placement is an authorization act, so it is its own verb gated `<resource>:move`, and clearing a
parent needs the same all-scoped grant creating a root does. Classification (product, standard,
system type, location type) stays on `PATCH`
([ADR-0064](/architecture/decisions/#adr-0064-placement-and-classification-are-mutable-after-create)).

```d2
direction: right
classes: { node: { style.border-radius: 8 }; key: { style: { border-radius: 8; bold: true } } }
component: component { class: key }
product: product { class: node }
location: location { class: node }
system: system { class: key }
standard: standard { class: node }
component -> product: is a
component -> component: parent
system -> standard: conforms to
system -> location: located at
system -> component: members
system -> system: parent
location -> location: parent
component -> component: depends on {style.stroke-dash: 3}
```

A location type's `allowed_parent_types` (location type ids and the `root` sentinel; empty means
unconstrained) is enforced on create and move. The location tree has no root: a fleet is a forest of
tops, and "everything" is the cascade's `platform` tier, never a location.

### Sub-components and sub-systems

Nesting is same-kind: a chassis over its line cards, a hall over its rooms. It feeds the cascade
(deeper wins) but not the health rollup: a system's health rolls up to its location, never through
the system tree ([health](/architecture/health/)). Containment implies nothing about power or
reach: a parent's reboot holds none of its children for being its children.

### Dependency edges: what a component needs, apart from where it sits

What a component **needs** is a separate fact from where it sits: a `component_dependency` row from
the dependent to its upstream, of one kind.

| Kind | Reads as | What it widens |
|---|---|---|
| `power` | fed from the named `outlet` of the upstream | a power command on that outlet holds the dependent |
| `host` | hosted by the upstream (a panel paired to a codec, a card in a chassis) | a reboot of the upstream holds the dependent too |
| `path` | reached through the upstream (a peripheral behind a gateway) | while the upstream's gates are closed, the dependent's in-band endpoints hold too ([outposts](/architecture/outposts/#implicit-reachability)) |

A `power` edge names its outlet and no other kind does; a component never depends on itself; an
edge that would close a cycle within its kind is refused; deleting either end deletes the edge.
Recording one costs `component:update` on the dependent and `component:read` on the upstream. The
edges feed a disruptive command's [hold set](/architecture/commands/#the-hold-set-follows-dependency-edges).

```bash
omniglass component dependency create codec-1 --upstream pdu-1 --kind power --outlet 3
omniglass component dependency list codec-1
omniglass component dependency delete codec-1 power pdu-1
```

## Ownership: the exclusive-arc

Everything observed, asserted or told attaches to exactly one owner through the **exclusive-arc**:
an `owner_kind` column, the matching typed foreign key (`component_id`, `system_id`, `location_id`,
`outpost_id`), and a CHECK that exactly the matching one is set. The sample lanes, `event` and
`command` carry it, so a system and an outpost own telemetry as first-class owners: a
system owns its health and what a push or a calc rule reports for it as a whole, an outpost its
self-health. A location owns its declared properties and calculated health, and no observed sample
([ADR-0422](/architecture/decisions/#adr-0422-a-system-owns-its-own-telemetry-and-a-location-owns-no-observed-sample)).
Alarms are component-owned today ([alarms and actions](/architecture/alarms-actions/)).

The config cells ride a sibling arc with a `platform` arm instead of `outpost`: a variable, secret
or tag binding is owned at `platform`, a location, a system or a component (a tag also at an
outpost; a secret never at a system), and resolves down the [cascade](/architecture/cascade/). The
DDL pattern is on [storage](/architecture/storage/).

## Lifecycle: delete today

A delete is refused while the row still has structural children or something still references
it: a location with child locations, a system with subsystems, a component filling a slot, a
product or type still classifying something. Deleting a system removes its memberships and keeps
the components. The console shows what is in the way ([entities](/operator/entities/#delete-and-what-is-in-the-way)).

:::design[Operational mode, tracked in #528]

## Operational mode: active, maintenance, disabled

Every entity has an operational mode, resolved down the cascade:

- **active** (default): collect, evaluate, act, enforce drift, count toward availability.
- **maintenance**: keep collecting, but hold action dispatch, observe drift without enforcing it,
  roll no impact into the parent's health (shown as "outage (maintenance)"), and exclude the window
  from availability. A window starts and ends on the [clock](/architecture/time/), or stays open
  until cleared.
- **disabled**: stop collecting and interacting entirely until re-enabled.

Each transition is [audited](/architecture/audit/), and maintenance on a system covers its
components.
:::

:::design[Decommission, purge, and the delete cascade, tracked in #528]
"Delete" becomes a soft **decommission**: out of placement, worklists and default views, history
kept until retention ages it out, re-commissionable. Open alarms resolve, pending commands cancel,
and bindings drop. **Purge** is the privileged, audited hard erase for a genuine mistake. An
outpost's decommission re-homes its tasks and revokes its credential.
:::

## How an entity is identified

Three things, and no fourth:

- **id**, a uuid: immutable, the primary key, what every foreign key and `audit_log.resource_id`
  stores, so a rename rewrites nothing.
- **name**, the renameable identifier an operator types and a URL or CLI argument carries. The rule
  is an allowlist, `^[a-z0-9][a-z0-9-]*$`, so a name never collides with a path separator, an
  accessor, a NATS wildcard or the router's `:verb` suffix. Renaming is its own custom method,
  `:rename`, gated `<resource>:rename`, with no `name` in the `PATCH` body
  ([ADR-0076](/architecture/decisions/#adr-0076-a-renameable-human-typed-identifier-stays-in-the-url-and-the-write-returns-the-uuid)).
- **label**, an optional friendly string a person reads ("HQ Boardroom DSP"). Absent is SQL `NULL`,
  never the empty string, and a surface with no label renders the name verbatim
  ([ADR-0118](/architecture/decisions/#adr-0118-the-friendly-string-an-operator-reads-is-a-label-and-unset-is-sql-null)).

A name is **unique within its placement**, not across the fleet: a component or system scopes to its
parent, else its location, else the fleet; a location to its parent, else the fleet. A top
location's name and an outpost's name stay fleet-wide.

Every exception is declared in `internal/storage/identity_shape.go` and rendered here. A
**keyspace** table's name is fleet-wide vocabulary a telemetry record is typed by, on the same rule:

## An address: a uuid or a dotted path

Every component, system and location resolves through one `{ref}` path parameter, three ways,
tried in order ([ADR-0089](/architecture/decisions/#adr-0089-a-uuid-is-the-address-a-dotted-path-is-a-positional-lookup)):

- a **uuid**, the address: the only reference the platform generates or stores;
- a **bare name**, resolved within the resource's own collection;
- a **dotted path**, a positional lookup: location segments from a top, an accessor that switches
  tree (`$comp`, `$sys`), then segments within it. `boi.17c.415a.$comp.dsp-1.dante-card-1` is a
  Dante card in a DSP chassis in room 415a. Quote it in a shell (`'...$comp...'`), which would
  otherwise expand `$comp` to nothing.

A bare name matching more than one row the caller can read is a **409** listing each match as its
dotted path and uuid; a name matching nothing is a **404**
([ADR-2334](/architecture/decisions/#adr-2334-an-ambiguous-name-is-a-409-listing-the-matches-a-missing-one-stays-a-404)).
A read carries the resolved `path` and `path_segments` beside two display-only renders, dashed
(`boi-17c-415a-display-1`) and compact (`boi17c415afp1`, the type's `abbrev` for the stem), which do
not resolve back.

## Generated names and labels

A name or label the platform derives is a default that **tracks until touched**
([ADR-0090](/architecture/decisions/#adr-0090-a-derived-value-is-a-default-that-tracks-until-touched)):
a stored value plus a pen (`name_generated`, `label_generated`) saying who owns it.

**Names.** A component or system created with no name mints its type's resolved `stem` plus the
lowest free ordinal in its placement bucket (`display-3`). A system suppresses the ordinal on the
first of a stem in its bucket (`board-meeting`, then `board-meeting-2`)
([ADR-0101](/architecture/decisions/#adr-0101-the-first-of-its-stem-in-a-bucket-carries-no-ordinal-and-the-mint-that-says-so-is-the-one-allocation-tests)).
A location type opts in through a nullable `name_rule`; no shipped type carries one, since a floor or
a room has a real-world name
([ADR-0103](/architecture/decisions/#adr-0103-a-positional-name-is-allocation-order-and-the-real-world-designation-is-a-label)).
While the platform owns a name it re-mints only when an input to the mint changes: a reclassify that
changes the resolved stem, or a move that changes the bucket. `:rename` freezes it, and
`:resetName` hands it back. Editing a rule renames nothing.

A create form previews the name a blank field will get through `:renderLabel`, which reads the next
free ordinal without allocating it. The create posts that name back as `expected_name`, and is a
**409** if allocation would now stamp a different one
([ADR-0104](/architecture/decisions/#adr-0104-a-create-form-shows-the-name-it-can-know-and-never-mints-one-to-preview-it)).

**Labels.** A label reads three rungs: the one an operator typed, else the one a rule rendered, else
the name. Rules resolve most-specific first: product, then the `component_type` chain, then the
global rule for components; standard, then the `system_type` chain, then the global rule for systems;
location type, then the global rule for locations
([ADR-0098](/architecture/decisions/#adr-0098-a-label-rule-reads-what-an-entity-is-never-where-it-sits)).
A rule is Go `text/template` over a closed map of strings and a closed grammar, checked when the rule
is edited (422 if it does not parse or reaches outside the grammar). A rule that fails on one entity
renders no label rather than failing the write.

A rule reads what an entity **is** and the label of the location it sits at, never its ancestry, so
a campus rename restamps nothing beneath it. Where the blast radius is one placement (a location's
relabel, a system's reclassify, a primary-membership change), labels restamp inside the act's own
