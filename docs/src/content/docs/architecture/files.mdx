Files keep the opaque bytes that go with a fleet (a firmware image, a config dump, a runbook, a
capture) searchable and deduplicated: a **file** handle over a content-addressed **blob** store,
behind the same Storage Gateway as everything else
([ADR-0029](/architecture/decisions/#adr-0029-files-slice-1-a-content-addressed-blob-store-and-a-tenant-wide-file-handle)).
To use them, see [the admin Files page](/admin/files/).

## Two layers: the handle and the blob

- **`file`** is indexable metadata: filename, content type, size and `sha256`. It owns no bytes. The
  filename is a human label with an extension, not a name, so it has no name rule and no uniqueness.
  A route takes the handle by uuid or by filename, and a filename shared by several files is refused
  with each candidate's uuid ([ADR-1133](/architecture/decisions/#adr-1133-every-operator-resource-answers-to-its-name-and-an-endpoint-is-its-component-and-its-name)).
- **the blob store** holds the bytes, keyed by `sha256`, so identical bytes are one blob.

Search and listing never touch bytes, and one blob can back many handles.

## Access: a permission and a sensitive tier

A file has no fleet placement: it relates to many things (one firmware image documents many device
types) or to none, so it is install-wide, gated by two layers:

- the `file:<action>` permission on every route (download rides `file:read`);
- a per-file `sensitive` flag reusing the secret sensitivity tier
  ([ADR-0025](/architecture/decisions/#adr-0025-secret-is-a-sensitive-resource-a-per-secret-admin_sensitive-flag-flips-a-secret-to-the-admin-tier)):
  a flagged file needs `file:read:admin`, is hidden from a lister, and is a non-disclosing 404 to a
  reader without it.

Unlike a secret the flag defaults false, so the viewer floor reads ordinary files.

## Content addressing

A blob is keyed by the hash of its bytes, which gives dedup, integrity (the hash verifies the bytes on
read), immutability, and stability for anything that references a hash. The key is the bare
`sha256` with no tenant id: isolation is per database, so dedup is global within one install and
never visible across installs. The default backend is `pgblobs`, a dedicated Postgres table, which
keeps the single-binary story. A file delete frees its blob synchronously when nothing else
references it.

:::design[Alternate blob backends, tracked in #248]
An S3-compatible object store for scale and a disk backend for local use, behind the same
`blob.Store` seam. The handle and the hash are identical across backends. Chunking and streaming for
very large blobs on `pgblobs` is open.
:::

:::design[Attachments, hash-refs from the signal lanes, and async GC, tracked in #242]
Attaching a file to components or device types is not built. Nor are hash-refs from a large
`log_line` body or a `collection.failed` raw payload (rows reference a hash, never inline bytes), nor
the async mark-sweep GC that collects a blob only when no reference points at it and a grace floor has
passed, coupled to retention.
:::

:::design[Tags on files, tracked in #191]
A file binds [tags](/architecture/tags/) as a flat per-file set: the shared key vocabulary, with no
cascade.
:::

:::design[Resource classification and clearance, tracked in #243]
A lattice that subsumes the binary `sensitive` flag across files and secrets, and an external-user
class that keeps an outside integrator from internal files.
:::
