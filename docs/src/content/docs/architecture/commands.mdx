## Actuation: the wire to the device

The issue records; the **wire actuates** (#815). The moving parts:

- **The queue is a per-node pull.** A node asks `og.v1.command.<node>` (request-reply, mirroring
  the worklist, the same reply-inbox confinement) and receives the commands whose owning
  component has a **driver-attached endpoint placed on it**, where that driver's spec **binds the
  command's type**. A command no driver binds is never delivered; its lifecycle is settlement's
  business alone.
- **Rendered at dispatch.** The server resolves the binding's request template against the
  command at delivery time: `${value}` is the intended value, `${arg.key}` an issue param
  (template references are validated at spec write). A substituted value carrying a control
  character (a `\r\n` that would inject a second framed line onto the device) refuses, so an
  operator-supplied value can never smuggle a command outside the driver menu; numbers render as
  plain decimals. The node receives a finished instruction (transport, target, the line to send),
  never a template. A binding that cannot render (a reference the issue did not supply) is
  recorded terminal on the row (`exec_error`) instead of redelivering forever. Exactly one
  actuating endpoint is chosen per command (only an endpoint whose driver binds the type is a
  candidate), so a command is delivered to one node, never once per node.
- **At-least-once, idempotent.** The pull marks the row `dispatched_at`; a dispatched command
  whose execution report never lands is redelivered after a silence interval, and past a delivery
  TTL it stops being deliverable at all (settlement's `timed-out` covers a command no node picked
  up). The node remembers each command's outcome per id, so a redelivery repeats the **report**,
  never the actuation.
- **The report carries the reply; the binding judges it.** The node reports execution on
  `og.v1.commandstatus.<node>` with the device's reply (any device answer counts as actuated; a
  failure carries its story into `exec_error`), and the row stamps `executed_at` once, confined
  to the node the command's **dispatched endpoint** is placed on: a report from any other node is
  rejected and logged, never a silent stamp, so a second node holding an unrelated endpoint on the
  same component cannot close a command it never received. Whether the device **did** it is
  settlement's judgment, made on the server: from the reply when the binding settles from the
  response, otherwise from the next observation the driver's polls (#814) report.

A **command** is the "do" half of the telemetry model, alongside a [metric or property](/architecture/properties/) (**know**) and an [event](/architecture/events/) (**happen**): it records what a component was **told**. Its registry is `command_type`, the driver-owned twin of the sample and event catalogs.

## The command_type registry

`command_type` describes every command: `(name, label, params_schema, settle_window_seconds, target_property_type_id, target_metric_type_id, official)`. Two facts are the driver's, not the abstract signal's:

- **`settle_window_seconds`**: how long the device physically takes to actuate (a projector warms up in twenty seconds, a matrix switch flips in one), so a difference from the reported value is not called drift until the device has had time to act. It is a duration, so the schema floors it at **0** and both write paths refuse a negative one: `Settle` tests `windowSeconds > 0`, so a negative window behaves exactly as zero does, and a value that is stored, read back, and then never honoured is worse than a refusal.
- **The two-armed target**: a **settleable** command names the value it sets in exactly one lane, `target_property_type_id` (`set-input` targets `video-input`) **or** `target_metric_type_id` (`set-volume` targets a numeric level), never both (a CHECK enforces the arc). A command with no target is **fire-and-forget** (`reboot`): it records the invocation and a caused event, with no value to settle.

The registry is seeded official and operator-extensible, official rows read-only, on the same shape as the [sample](/architecture/properties/#the-two-catalogs) and [event](/architecture/events/#the-event_type-registry) catalogs (a console **Command Types** page, `/command-types` CRUD gated by `command_type:*`).

## Issuing a command composes the whole model

Issuing is one transaction writing three things:

1. the **`command`** row (the invocation: owner, command_type, params, actor, `status='issued'`), over the same [exclusive owner arc](/architecture/properties/#ownership-the-exclusive-arc) as every sample and event;
2. a **caused `event`** ([`origin=caused`](/architecture/events/#events-caught-caused-derived-scheduled), typed `command-issued`), the record that a command happened, which only a command writes (its writer class is `command-lifecycle`, so a push, a node, a driver or an event rule landing one is refused, [ADR-1100](/architecture/decisions/#adr-1100-legacy-rows-and-stored-declarations-honor-the-one-writer-ruling)); and
3. for a settleable command, an **`intended`** series row in the target lane (`provenance=intended`, its `ts` the moment of issue, `command_id` naming this command as its lineage), the **told** in the want/told/is pivot.

`POST /components/{name}/commands:issue` is the write, gated by `command:issue` and scope-injected
through the component. The **fence is the issue scope, not the read scope**
([ADR-0117](/architecture/decisions/#adr-0117-an-actuation-is-fenced-by-the-permission-that-authorizes-it)):
`command` is a component-tier resource, so a principal holding a wide component read beside a
room-scoped command grant may command that room and no more. The read scope decides only which
refusal it is owed, a non-disclosing 404 outside it and a 403 for a component it can see but not
command ([the three-way split](/architecture/identity-access/#the-three-way-status-split)).

## Settlement: the verdict is computed, the outcome is recorded

A command's effect is judged as a pure function of the intended value, the observed value, and the settle window:

- **none**: nothing was told (fire-and-forget, or no intended value).
- **settled**: an observation taken at or after the intent matches it, as soon as one arrives; or,
  past the window, the latest observation matches.
- **pending**: still within the settle window with no matching observation yet, so a difference
  from observed is not yet drift.
- **failed**: past the window, observed does not match (or is absent).

This is the windowed form of the `told` versus `is` comparison each row of the [properties read](/architecture/properties/#reconciliation-want-told-is) carries.
The window bounds how long a command waits for its evidence, not when it may settle
([ADR-0141](/architecture/decisions/#adr-0141-a-command-settles-when-its-evidence-arrives-from-its-reply-first-and-observation-second)).

**Where the evidence comes from is the driver's to declare.** Each command binding in a driver
spec says how its commands settle:

- `settle: { from: response, extract: { regex: ... } }`: the device's reply carries the new value
  (`SET INPUT hdmi3` answers `INPUT hdmi3`). The server reads it when the execution report lands
  and settles the command if it matches the intent or fails it if not. For a property target the
  value is also recorded as an observation on the dispatched endpoint, held to the property's
  validation like any telemetry (a value outside it fails the command and records nothing) and
  written only when it changes; a metric target is judged without a recorded sample.
- `settle: { from: response, success: { regex: ... } }`: the reply only confirms (`OK`). A
  matching reply settles the command; any other fails it.
- `settle: { from: observe }`, the default: the reply decides nothing, and the next observation of
  the target settles the command. The settle check runs when an observation lands, not only at
  issue and on reads.

In every mode an execution error fails a response-settled command at once, and **a sweep** the
server runs every few seconds judges each command whose window has passed, so one that no reply
and no observation settles reaches `timed-out` without waiting for another command or a read.

**Which observation a command is judged on** follows what its
[instance](/architecture/properties/#the-instance-dimension-many-values-of-one-name-on-one-owner)
says ([ADR-0456](/architecture/decisions/#adr-0456-an-instance-names-which-value-of-one-key-on-one-owner-a-row-is-and-an-owner-level-read-reduces-across-every-instance)). A command that names an instance is judged on that series alone. One
issued with no instance is judged on the series of the endpoint that carries it, where that
driver's observations of the target land: the endpoint it was dispatched over, or, before a node
takes it, the endpoint queued to carry it (the first, by name, whose driver binds its type). One
with no instance that no endpoint can carry (no endpoint's driver binds its type) is an owner-level
intent, judged on **every** live observed instance of its target: settled when any instance agrees,
failed past the window when instances were observed and none agrees, timed out when nothing was
observed. A live instance leaves out a **retired observer**, an endpoint since deleted whose last
reading would otherwise stand forever. A command still queued, which no node has taken, never
reached the device, so its window closing is a timeout that says where it stopped, whatever its
carrier last read, never a failure. An observation runs the settle check of every command judged on
its instance and of every owner-level one, and the computed verdict a command's issue answers with
reads the same observation the recorded outcome did.

**A zero window is terminal by construction, never by arithmetic**
([ADR-0108](/architecture/decisions/#adr-0108-settlement-reads-one-clock-and-a-zero-window-is-a-statement-of-intent)).
`settle_window_seconds: 0` is the way to say "settle immediately", which is a claim about intent
rather than about elapsed time, so the verdict for such a command never consults a timestamp and
never comes back `pending`. And **the comparison reads one clock, the database's**: a sample's `ts`
is written by Postgres, so the `now` a settle-check judges against is read from Postgres too, in the
same transaction. A server whose clock differs from its database's gets the same verdict either way.

Beside the computed verdict, the `command` row **records its lifecycle**: `status` is `issued`
until a terminal `settled`, `failed`, or `timed-out`, and `settled_at` stamps the terminal moment
(a CHECK ties the two: `issued` exactly while `settled_at` is null). The recorded status carries
the finer vocabulary the verdict collapses (failed versus timed-out; a fire-and-forget records
`settled` while its verdict stays `none`), so a stuck command is distinguishable from one nobody
has checked ([ADR-0079](/architecture/decisions/#adr-0079-five-telemetry-lanes-and-property-stops-being-the-genus)).

## Reading a command: from issue to settlement

A command is read whole, under the component it was issued to (#1155): `GET
/components/{name}/commands/{id}` for one, `GET /components/{name}/commands` for the history, newest
first, narrowed by recorded `status` (`issued` is what is in flight now), by when it was issued
(`since`, `until`) and a page size (`limit`). A command has no name, so its id under its component is
its address, the component taking every spelling the component routes take. Each carries:

- **what it was told**: the command type, its params, the value it set (`intended`, by the
  `command_id` lineage) and the property or metric it sets;
- **its state machine**, a time per transition: `issued_at`, `delivered_at` (a node last took it from
  its queue), `executed_at` (the node's report landed) and `settled_at`, beside the recorded `status`;
- **where it sits now** (`phase`), derived on read and never stored: `queued` for its node,
  `delivered` to it (a binding that settles on observation, so the reply decides nothing),
  `awaiting-reply` (the reply settles it), `awaiting-observation` within its window (the report is in,
  or no endpoint can carry it and only a sample of its target can settle it), and once terminal its
  status. Its `deadline` is when the window closes;
- **how it settles** (`settle_mode`: reply, observation, or none for fire-and-forget), read off the
  binding of the endpoint it rides, and **what carried it**: that endpoint, its node and its driver;
- **the evidence and the why**: the component's `reply`, the observed sample when an observation
  decided it (`observed`), what decided it (`settled_by`: issue, reply, observation, or the window),
  the execution error, and a `reason` in words (the reply that confirmed it, the value observed
  instead, or, on a timeout, where it stopped: answered with nothing observed, delivered with no
  report, queued for a node that never took it, carried by no endpoint);
- **who issued it**, by name and uuid, the actor on its audit row.

**The reply is masked before it is stored.** A reply crosses from a component the operator does not
control, so the execution report's reply and error are masked of the dispatched endpoint's secret
fields in the forms a component commonly echoes them (raw, url-escaped, JSON-escaped, html-escaped,
base64, in any case, and a basic login's authorization value) and of any pair, element, header or
config keyword the text labels a credential, then made valid text and capped at 4 KiB, before they
reach the row; the binding's judgment reads the reply whole. The masking fails closed: a server that
cannot read the endpoint's secrets withholds the reply and the error rather than store them
half-masked. The masking is one primitive (`internal/redact`) that the node's own http scrub runs
too. A form it does not know (a hash, a partial echo) is stored as echoed, which is why a driver
should not ask a component to echo its login
([ADR-1155](/architecture/decisions/#adr-1155-a-command-is-read-whole-its-evidence-kept-and-masked-and-an-issue-may-wait)).

**Each terminal status lands on the component's timeline.** Settling, failing and timing out write
`command-settled`, `command-failed` and `command-timed-out`, caused events naming the command and
linked from the row (`settled_event_id`), in the transaction that records the outcome. They carry no
evidence and no reason: those stay on the command, behind `command:read`. They are
`command-lifecycle` keys beside `command-issued`, so only a command writes one, and a failure reads
by its type rather than out of a message. A fire-and-forget command, settled by its issue, writes no second event.

**Reading needs `command:read`**, resolved on the component tier with the same split an action's
target makes: a component outside the caller's `component:read` is the non-disclosing 404, and one
inside it whose commands the caller may not read is the truthful 403
([identity and access](/architecture/identity-access/#the-three-way-status-split)). The viewer floor
holds it, and the read floor gives every issuer it wherever it may issue.

**An issue may wait.** `wait` holds the issue until the command is terminal or `wait_timeout` passes
(1 to 120 seconds, 30 by default), answering with the command as it stands either way, its phase
saying where. It polls quickly at first (a reply settles a command within a node's cycle) and backs
off to once a second, and once the deadline passes it judges the command itself, so a timeout answers
at the window rather than at the next sweep. At most 64 waits run at once across a server and 4 per
principal; a wait past either is a 429 refused before anything is issued, so a refusal leaves nothing
behind to retry around.
