## AI acts through the same seams as any user

AI is **not a side channel**. It reaches the fleet through the same three seams every actor uses: the **API** (no private back door, no direct database path), **IAM permissions** (`<resource>:<action>` on every route), and the **Storage Gateway scope** (the ABAC visible-set on every applicable query). What stops a human stops the AI; there is no elevated AI lane.

The richest seam is the **generated [MCP server](/architecture/api/#also-an-mcp-surface)**: an MCP tool call is a call to a real API operation, carrying the **acting user or machine user's** token through the same routes, permissions, scope, and [audit](/architecture/audit/) as the SPA or the CLI. It is a generated client like the others: the tools are the operations stamped for MCP in the server's Go source, listed in the [MCP tools reference](/reference/mcp/), a curated catalog rather than a raw one-method-per-tool dump. Each tool tells the client what it may assume (read-only, destructive, idempotent, open-world), so the agent's own client can hold a write for its user's confirmation. The catalog is **credential-blind**: no tool takes or returns a credential in plaintext, so a secret's value or a minted token never enters a model's context ([ADR-2025](/architecture/decisions/#adr-2025-the-mcp-catalog-is-credential-blind-and-reads-the-fleets-alarms-in-one-call)). An agent connects at `/mcp` over streamable HTTP, or over stdio with `omniglass mcp`; see [connect an agent](/guides/agents/).

Tools say what can be done; **skills** say how the house does a job with them. Each is one `SKILL.md` (the Agent Skills format: front matter, then a Markdown workflow) embedded in the binary and served as an MCP prompt, so it ships with the release whose tools it names and a test fails any tool it names that the catalog lacks. A skill carries no permissions of its own: the [MCP skills reference](/reference/mcp/skills/) reads them from the gates of the tools it uses. Every skill reads before it changes anything, asks before every write, and never asks for a credential: a poll or a command runs on the server with the credentials bound to the endpoint, so the agent never needs one, and a skill tells it not to repeat one a tool's answer quotes. Masking credentials out of an answer is the route's job, not the skill's.

## Provenance and audit

The write attributes to the **acting user** in [`audit_log`](/architecture/audit/), so the trail names a responsible actor on every move, and the row's **channel** marks how it arrived: `mcp` for a tool call, with the client the agent declared beside it, and `omnibot` for omnibot's own. The `omnibot` channel is stamped from the credential, never from a declared client name: only an agent token minted for the omnibot channel alone (and only the `omnibot` agent may be), arriving over MCP, writes it, and such a token is refused on the direct API. The marking rides alongside the actor, never replacing it.

:::design[Target design (ADR-0001): AI as a governed capability]

AI in Omniglass is a **capability spanning assistive to operational**, governed exactly like any other actor: it enriches and explains at one end, proposes and acts at the other.

From assistive toward operational:

- **Enrichment**: context, a likely cause, a suggested next step on the occurrence in front of the operator. Read-only, inline.
- **Diagnosis and reporting**: troubleshooting, root-cause analysis across correlated signals, report generation (health summaries, incident write-ups, period reviews).
- **Natural-language surfaces**: NL business query ("which rooms had the most ghost meetings last month"), NL configuration, NL template development. The first is omnibot, the in-app assistant that monitors a component and builds its driver, an MCP client of this same server (epic #1161).
- **Operational actions**: acting on an operator's behalf (room and meeting rebooking, platform configuration), under that operator's grants.
- **Closed-loop automation**: diagnose-and-fix for a known failure class. **Human-in-the-loop is the default**: a mutating action is gated until the class has earned looser handling.

Every AI-produced output (an explanation, a drafted driver, a report) is **marked as AI-sourced**, keeping the capability assistive, not authoritative: a reader can always tell what came from AI, weigh it, and trace it.
:::

:::design[Human-in-the-loop gating, tracked in #1161]

Mutating AI actions can require **operator sign-off**, given in the person's own client from the tool's resolved policy before the call is sent: nothing waits on the server, a declined call is never sent, and a confirmed one is audited as the agent's like any other call; read and diagnostic actions run ungated within the acting user's scope. A **policy on AI-sourced mutations**, not a separate authorization model: the gate is an extra confirmation on top of the user's grants, never beyond them. omnibot never executes a write its user has not confirmed; an external agent's own client gates its writes from the tool annotations.
:::

omnibot's half is built (#1166): its loop reads each listed tool's resolved policy, runs an `always` tool, puts an `ask` tool to its person (a tool with no policy is treated as `ask`), and is never offered a `never` tool. A declined call does not run, and the model is told so. With no terminal to ask, every `ask` is declined. The token it runs on is minted from its person's for one day and the omnibot channel alone, and revoked when the run ends, so every call is the route's under that person's grants, audited as `omnibot` acting for them; an agent token cannot mint a token, so omnibot cannot be run on one.

The loop reports each step as it happens, for whoever drives it to stream (#2120): the model's text for a turn, each call it proposes (by the provider's call id, with its arguments and the tool's policy), what was decided for that call (`called`, `declined`, `refused`, or `waiting`), and what the model is told came of it. An `ask` need not block either: a loop set to pause stops at the ask and returns the conversation so far with the call it waits on, and continuing that conversation with its owner's decision answers the call, finishes the turn's remaining calls in order, and runs on. An approval continued later ends in the same conversation an inline approval does; a declined one runs nothing. Where a paused run waits is its holder's choice: the CLI asks inline, so a run there never pauses.

**A conversation is kept for its owner alone** ([ADR-2113](/architecture/decisions/#adr-2113-a-persons-omnibot-conversations-are-theirs-alone)). A person's omnibot conversations are stored by name under `/assistant/conversations`, behind `assistant:use` (which `viewer` carries), and every read and write carries the owner as its predicate: anyone else, an admin or the platform owner included, finds a 404 on every verb and an empty list. The one exception is [impersonation](/architecture/identity-access/), which sees what its target sees, conversations included, and audits an act-as write with the real actor. A client appends a turn by naming the last message it saw, so two clients cannot interleave one; the append is audited without its content. A run that paused on an ask keeps the write it waits on with the transcript, as a marker naming the open call, and nothing on the server acts on it: there is no server-side pending approval ([ADR-2113.2](/architecture/decisions/#adr-21132-a-paused-omnibot-run-keeps-only-its-transcript)). The owner continues it in their own client, which rebuilds the proposal from the transcript's open call and the live tools (a marker naming no open call is refused) and decides it the way an inline ask is decided. `omniglass omnibot --resume <name>` is that client on the CLI. A conversation is pruned `assistant.conversation_days` (30 by default) after it last moved.

**The server runs omnibot too** ([ADR-2121](/architecture/decisions/#adr-2121-the-server-runs-omnibot-as-the-person-streaming-ag-ui)). `POST /assistant/conversations/{name}:run` takes an [AG-UI](https://docs.ag-ui.com/) run input, runs its last user message as the caller's omnibot over the stored conversation, and streams the run back as AG-UI events: the model's text, each call with its arguments, each call's result, and the run's end. The stored transcript is the conversation; the history a client sends is not believed. The run holds a token of its own, minted for the person as the CLI mints one (the `omnibot` channel alone, for the run's 30 minutes at most) and revoked when the stream ends, and calls its tools in process through the same router a remote MCP call takes, so the model never sees a credential and every write is audited as `omnibot` acting for the person. An `ask` ends the run on an interrupt naming the call; the run's new messages and the waiting call are kept with the transcript, and a later run whose `resume` answers that interrupt runs it or declines it. A run claims the conversation before any tool runs, so a second run, two resumes of one waiting call included, is a 409 and a call runs once; a run that dies frees its claim when its 30 minutes lapse. Only the person, as themselves, runs their conversations: an agent token or an impersonation session is refused, so a run's actor is always the person whose conversation it is. A server runs omnibot only with a model configured; until a live provider lands, `OMNIGLASS_OMNIBOT_REPLAY` names a recording it plays.

**Credentials never enter a model's context.** Beyond the credential-blind catalog, the one path by which a person hands omnibot a credential keeps it out too (#2112): in omnibot's chat, `/secret` reads the value with the terminal's echo off, creates the secret with the person's own token (so the create is theirs, and an agent token's lack of plaintext-in routes never bends), and adds only the secret's reference (name, type, owner) to the conversation. The model binds it by that name, and the server uses it on the model's behalf. omnibot does not scan typed prompts for credentials; `/secret` is the path, and a value typed as a prompt is the person's to have sent.

The install-wide half of that policy is built ([ADR-2063](/architecture/decisions/#adr-2063-an-install-sets-always-ask-or-never-per-class-of-operation-for-every-agent)): an admin sets `always`, `ask` or `never` for each class of operation (read, write, destructive, credential destination) in the `agent` settings namespace. The server refuses a `never` class to any agent request (an agent token, or any call over MCP) and audits the refusal as the agent's; `ask` is the client's to honor, carried on every listed tool's `_meta`. There is no server-side pending approval: a person approves in their own client. Two narrower layers sit on top ([ADR-2088](/architecture/decisions/#adr-2088-role-and-per-tool-overrides-narrow-the-agent-policy-strictest-wins)): a **role** override sets a class for the agents of anyone granted that role, and a **tool** override sets one operation. Each only narrows: the strictest of the platform, every role the person is granted and the tool wins, and the resolved policy names the layer that set it, so a refusal says whether a tool, a role or the class refused it. See [what an agent may do](/guides/agents/#what-an-agent-may-do).
