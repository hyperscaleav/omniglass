Expressions let an operator reshape and judge collected values in plain text wherever the
platform needs a small computation, with exactly one language to learn: every site goes through
**one engine, Omniglass expressions**, built on **Expr**
([expr-lang/expr](https://github.com/expr-lang/expr), pinned at v1.17.8). The engine is
`internal/expression` (#524); its first consumer is the event rule's criteria
([alarms and actions](/architecture/alarms-actions/#the-event_rule)).

## Compiling, once

A site declares its environment as a Go struct (the names an expression may use, their types and
docs), the type an expression must yield (a criteria yields true or false), the builtins it admits
and its run budget. An expression compiles against that declaration: a name outside it, a result of
another type, or a parse error is refused with a **diagnostic** carrying the line, the column and an
operator-readable message (a nested binding is named by its path, `component`, never by a Go type). A
name nothing binds is said by name (`unbound`, so an editor can offer to bind it), and a `let` that
would shadow a binding is refused where it is declared. Expr trusts a function call's type on its final
check without looking inside its arguments again, so the engine clears it, and a fault inside a call's
argument (an unknown name in `max(fan)`) is never passed over.
A compiled program is **cached** by its source and its site's declaration in a bounded cache, so a
hot path (a criteria judged per sample) never recompiles; an event rule also holds its compiled
criteria per rule version, a failed compile included.

## Safety

Expressions are **sandboxed**: no I/O, no network, no unbounded loops, bounded execution.

- **An allowlist of builtins.** Every Expr builtin is off, and **each site declares the builtins it
  admits**. A builtin is admitted only once vetted: its cost linear in what the run is charged for,
  its output no larger than its inputs. The criteria set is comparison, arithmetic, `in`, `contains`
  / `startsWith` / `endsWith`, `matches` with a constant pattern (capped in compiled size, and charged
  its subject's length times that size), `len`, `abs` / `ceil` / `floor` / `round` / `min` / `max`
  on numbers only, `lower` / `upper` / `trim` / `trimPrefix` / `trimSuffix`, and `all` / `any` /
  `none` / `one` / `count` / `filter` over a bound list with no predicate nested in another.
  Equality and `in` take scalars and lists of scalars (and a key in a map), never a record, a map,
  or a list of lists, whose deep comparison no charge covers.
- **List functions** (#1018) are vetted the same way, each with its cost argument (one charged pass
  over a list, one value out), and admitted by name where a site binds lists: `max` and `min` over one
  list of numbers (or over numbers), `avg`, `sum` (with or without a predicate), `majority` (the most
  common text or bool, its strings charged their bytes, a tie to the value that sorts first), and the
  one-list `any` and `all` over bools beside their predicate forms. A list function given anything but
  its list is refused at compile time on the argument. Their names, like every builtin's, can never be
  bound, so admitting one later never changes what a stored expression means. Expr parses `any`, `all`
  and `sum` as predicate builtins only, so a call of one with a single argument is told apart before
  parsing, lexically, and renamed in place to the engine's own function of the same length, which keeps
  every position in the source where the author wrote it. Builders and encoders (`map`,
  `reduce`, `repeat`, `replace`, `join`, `uniq`, `flatten`, `toJSON`, the range `..`) are never
  admitted: their cost is native work that no input charge bounds.
- **Determinism.** The clock and zone builtins (**`now`**, **`date`**, **`duration`**,
  **`timezone`**) can never be vetted; a time an expression needs is bound by its caller as data.
  An expression calls builtins only, never a method or a bound value, and a site's environment
  holds concrete data types (no interface, so no value whose behavior is chosen at run time). A `$`
  name (Expr's dynamic `$env`, or the engine's own plumbing) is refused, so a site's bindings are
  the whole namespace.
- **Caps and budgets.** A source is at most 4096 bytes and 1000 syntax nodes, and a list or map
  literal at most 64 entries. A run is bounded by **its site's budget** of what it allocates and
  what it walks, deterministically; a criteria's is small, and no site's exceeds a fixed ceiling. A
  wall-clock deadline backs the budget for charged work only: it cannot interrupt a native call,
  which is why the allowlist exists.
- **Values are data.** A value bound in the environment (a sample's text, however hostile) is
  evaluated literally and never executed. Integer arithmetic wraps on overflow, as Go's does,
  rather than failing.
- **Compiled unoptimized, and refused rather than crashed.** Expr's optimizer is off: in v1.17.8 it
  rewrites `filter(list, p)[0]` and `[-1]` into `find` and `findLast` and loses the record's field
  table on the way, so a field read on the result (`filter(members, .has.a)[0].value.a`) panicked
  in Expr's compiler. It comes back on when upstream is fixed (#1006). Nothing is charged
  differently without it: every charge wraps its operand before Expr would fold it. A panic in any
  compile stage, the engine's own or Expr's, is refused as a type error naming the stage and the
  construct it was on, never a crash or a nil pointer.

## Sites: the bindings, builtins and budget of each

Each place an expression is written is a **site**, declared once in code. The tables below are
generated from those declarations (`make gen`), and **`POST /expressions:validate`** (`omniglass
expression validate`, gated `rule:read`) answers from the same ones: given a site, a source and,
for criteria, the sample key (for calc, the output key and the rule's inputs), it says whether the
expression compiles, with each diagnostic's line and column, and returns the site's bindings,
builtins and budget. The **calc** site (#995) is the first whose bindings are authored with each
expression: a calc rule's inputs, each bound by its alias as the list of its current values (#1018),
from a struct type built when the rule is written, so its table describes them rather than listing them,
with the list functions it admits and the names an alias may not take (both generated, and the
console's alias check is generated from the same list). The console's **expression field**
(the rule drawer's **Write as an expression**, #960, and the calc rule's reduce) is that route's face, a
code editor on CodeMirror 6 (#1000) driven entirely by the route's answer: Expr highlighted as it is
written, completion of exactly the site's bindings and builtins (as a word is begun, or on Ctrl-Space),
a binding's doc on hover, and each diagnostic underlined where it sits as well as pointed at beneath under
its line and column, with the site's bindings and functions listed under the field. The field asks for
the site's vocabulary while the source is still empty, so the first word completes too. A site's form
may offer start-from templates (the calc rule's list functions, inserted with the cursor in the slot)
and an action on a name nothing binds (the calc rule's **Bind it to a key**, in the fault's tooltip and
beside it). The editor is named by its field's visible label. The editor is a chunk of its own, loaded
only by a page with an expression site; a page that cannot load it says so and refuses the source. Built today:

## Diagnostics: clear messages and quick fixes

Expr's own refusals are accurate but speak the checker's language (`sum(members, .has.t) > 0` is
refused as an operator mismatch at the `>`, when the mistake is the `sum`), and an expression can compile
and still probably be wrong. So the engine keeps a **registry of diagnostics** (#1021,
`internal/expression/diagnostics.go`): each common mistake is one declared rule with

- a stable **code** (`sum-of-bools`), a **severity** (an **error** refuses the expression; a **warning**,
  probably wrong, and a **hint**, could be simpler, ride along with one that compiles and never refuse it),
  and the **sites** it applies at (criteria, calc, or every site; a site names itself on its environment);
- a **trigger**: a **refine** rule runs when the engine refuses an expression and recognises the shape
  behind the refusal, replacing the message with a clearer one at the place the mistake is (it explains a
  refusal, so it is always an error); a **lint** rule runs on an expression that compiles, on its checked
  tree, and flags a likely mistake;
- a **matcher**, a pure function over the typed tree (and, for a refine rule, the refusal), returning the
  positions it found;
- a **message**, and an optional **fix**: one text edit (a range and its replacement) an editor offers as
  a quick fix;
- **fixtures** beside it in Go: expressions it must give its diagnostic for and must not, each compiled
  against a site-shaped environment, with the fixed source a fix must yield (which must compile without
  it). A rule without both kinds of fixture refuses to register, and a fixture that disagrees with its rule
  fails the build.

`Compile` and `Check` run a site's rules once per compile, so a cached program carries its warnings and
hints, and a matcher that panics is a bug in the rule: the expression is judged as if the rule were absent,
never refused by it and never crashing the server.

The first four rules (#1054) are the mistakes authors made first: **`sum-of-bools`** explains a `sum` over
true-or-false values (`sum(members, .has.t) > 0`) as the count it meant, on the `sum`, with the fix
`count(...)`; **`float-equality`** warns that `value == 1.5` is seldom exactly true of a measured number
and suggests a range; **`count-equals-len`** hints that `count(xs, p) == len(xs)` is `all(xs, p)`, with
that fix; and **`unused-alias`** warns of a calc rule's input the reduce never names (the site declares
its aliases as the expression's inputs), which the rule reads for nothing. A warning never refuses a
rule: `value == 1.5` still saves and judges.

## Extended with Omniglass functions

Expr is the core, chosen because it is transform-oriented, fast, and sandboxable: a rich operator
set suited to reshaping collected values (`raw / 100.0`, `int(groups[1])`, `groups[2] == 'true'`).
On top ride **Omniglass functions**: helpers Expr does not ship, including frame **`encode` /
`decode`** and the output-format helpers (**hex / ascii / base64**) that binary and raw-TCP
protocols need, each vetted into the sites that need it. The engine is **not pluggable**: one
dialect everyone authors in; where an expression is not even needed, prefer a straightforward
native path.
:::

## Unit conversion: `convert(value, "<unit>")`

Stored values are always in their `property_type`'s **canonical unit**; **`convert(value,
"<unit>")`** lets an operator author against a non-canonical one. The **source unit is
inferred** from the bound property's canonical unit; the **target** must be a registered unit
in the **same family** (a compile error otherwise). The conversion comes from the
[unit registry](/architecture/properties/#units-one-canonical-unit-per-metric): `to_canonical` /
`from_canonical` transforms, **affine** or an **Expr** for the rare nonlinear one. So
`convert(value, "fahrenheit") > 100` reads in Fahrenheit while storage stays in canonical
celsius. A function rather than a per-unit method: data-driven, general, available wherever
expressions run.
:::

## In-scope bindings

Within a function run the engine environment exposes: `$var:<name>` (config/secret through the
cascade), `$prop.<key>` (properties, emitted and readable for branching; was `$dp.<key>`,
renamed with the ADR-0065 vocabulary), `$steps.<id>.*` (ephemeral scratch), `$event` (a listen
payload), and the
extractor-local inputs a step prepares for its `value` leaf (`raw`, `groups`, `node`, `item`).
Rule and view contexts bind their own documented environments (the candidate entity, the
property, the resource row).

## Configuration values and secrets

Operator-supplied configuration values are bound as **data in the environment**, never spliced
into expression text, so a hostile value is evaluated literally and never executed. Secret
fields rendered into a request are masked at interpolation time and never surface in a log
line, error string, or property label.
:::

:::design[Divergence, tracked in #430]

## Divergence and `disagree(A, B)`

**`disagree(A, B)`** compares two provenances or sources of one key: config drift, reconcile
conflict, and cross-source disagreement are all the one operator, surfacing **divergence**,
the universal anomaly signal. Reading both sides as inputs (never writing a verdict back into
either) keeps the pipeline's DAG acyclic.
:::
