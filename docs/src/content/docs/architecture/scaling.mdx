Omniglass is **one Go binary**, a packaging decision rather than a ceiling. The same artifact runs a
laptop demo and a fleet of thousands of systems; it grows by measured topology, and the figures that
say when to grow are reported by the running server itself. To deploy it, see
[deployment](/deployment/).

## Two run modes, one binary

The binary is a modular monolith: one codebase, modules behind clean seams (the
[Storage Gateway](/architecture/storage/#the-storage-gateway-and-tiering) is the only path to the
database, outposts talk to the server only over the bus). It runs two ways:

- **`omniglass server`**: the API, the console (embedded in the binary, not a separate service), an
  embedded NATS server with JetStream, the ingest consumers, and the background loops (calc, rule
  reconcile, settlement, retention). It runs against a Postgres the install brings
  ([storage](/architecture/storage/)).
- **`omniglass outpost run`**: collection, at a site or centrally for cloud and SaaS sources. It
  connects out to the server's bus and needs nothing inbound ([outposts](/architecture/outposts/)).

`omniglass migrate` applies the schema, and the server's boot refuses a schema newer than it knows.
A release ships as binaries for each platform, a multi-arch container image and a Helm chart.

Until embedded Postgres lands, the one-command way to run everything on a laptop is the
[lab](/developer/lab/): Postgres, the server and an outpost with a simulated fleet, as containers. It
is a place to learn, not a deployment: its data is disposable and its sign-in well known.

:::design[Embedded Postgres, tracked in #19]
The server brings Postgres up in process as a managed subprocess, a real Postgres rather than SQLite,
so one container with no external setup is a complete install.
:::

## Coordination: the bus moves, Postgres remembers

Postgres is the system of record. NATS JetStream is how work moves: an outpost's worklist and
heartbeat ride request-reply on its own subjects, its telemetry rides the `OG_TELEMETRY` stream, and
commands are queued to it. Postgres is never used as a message bus.

The ingest stream is consumed in **lanes**: each outpost's batches are filed under a partition of its
name, and each partition is a durable consumer with one batch in flight, so an outpost's batches land
in the order it sent them while the partitions land side by side
([ADR-1896](/architecture/decisions/#adr-1896-ingest-lands-on-a-lane-per-partition-of-the-nodes-name-in-order-per-node)).
There are four by default, `OMNIGLASS_INGEST_PARTITIONS` sets from 1 to 64, and each lane confines
and persists inline.

:::design[The two-lane data plane, tracked in #2611]
Samples move on a data lane to a persistence consumer and a rule engine consumer, and every row born
in a Postgres transaction is fanned onto the bus by a leader-elected CDC publisher reading the WAL
([messaging](/architecture/messaging/#two-lanes-one-bus)).
:::

## Ingest: one batch per tick

What an outpost costs the server is set by how many transactions its telemetry makes, not by its
sample count. An outpost publishes **one batch a tick**, a group per task
([outposts](/architecture/outposts/#delivery-a-batch-lands-once)), and the batch lands in one
transaction under its receipt
([ADR-0311](/architecture/decisions/#adr-0311-a-telemetry-batch-lands-once-in-one-transaction-under-its-receipt)).
That transaction costs a fixed dozen or so statements, plus a term for each series the batch carries
twice, each judged sample that fires a rule, each settled targeted property, and each conduit group
carrying identified samples; with none of those, a batch of one group and a batch of fifty cost the
same ([storage](/architecture/storage/#ingest-lands-a-batch-in-one-transaction)).

| Corporate at 1,000 systems, the busiest outpost | Target |
| --- | --- |
| Samples per batch | 40 or more |
| Statements per sample | about 0.5 |
| Batches a second, all outposts | 18 or fewer (one flush a second per outpost) |
| Receipts a day | under 1.2 GiB ([ADR-1699](/architecture/decisions/#adr-1699-the-receipt-packs-its-accounting-and-its-target-is-12-gib-a-day)) |
| Ingest lag p99 | under 5 s |

These are targets. `omniglass lab measure` prints the measured figures for a scale lab (batches,
samples per batch, receipts a day, WAL bytes a sample, the ingest lag percentiles, redeliveries, and
each lane's busy fraction) ([measuring a scale lab](/developer/lab/#measuring-a-scale-lab)). A figure
is always quoted with the scenario and size it was read at and compares only with the same: every
measured lab level runs the `corporate` scenario, at 20, 300, 1,000 or 3,000 systems
([which fleet each level measures](/developer/lab/#which-fleet-each-level-measures)).

A faster lane is a win only if it still lands everything, so the same run reads every telemetry
kind's **loss ratio** across the outpost hop and the ingest hop, `(in - out) / in` with 0 healthy,
from the accounting each batch carries on its receipt
([messaging](/architecture/messaging/#accounting-every-item-the-loss-ratio)). The
[perf gate](/developer/lab/#checking-against-the-baseline) fails a run with any loss above 0, naming
the kind, the hop and the cause. The accounting packs into integer arrays on the receipt rather than
new rows, and receipts are pruned at a day, so their size is a standing table of about 1 GiB a day at
the rate above, about 1% of the metric table the same fleet writes.

### Scale up or scale out: what the figures say

A running server reports these on its own platform component every report window
([messaging](/architecture/messaging/#measuring-the-pipeline),
[workers](/architecture/workers/#measuring-the-ticks)), so the evidence is the fleet's own history.
Read them together:

- **A lane is the ceiling.** `ingest-lane-busy` near 1, `bus-consumer-pending` growing window over
  window and `ingest-lag-max` climbing: the busiest lane is saturated. A bigger box helps only as far
  as it shortens each landing; past that, more partitions spread the outposts across more lanes.
- **The database or the process is the ceiling.** `db-pool-wait-count` a nonzero share of
  `db-pool-acquire-count` with `db-pool-acquired` at `db-pool-max`, or `process-cpu-seconds` over the
  window near the server's cores, while no lane is saturated: scale up (more cores, a larger pool, a
  faster database).
- **The database is out of connections.** `db-connection-count` near `db-connection-limit` while the
  pool shows headroom: other clients hold the rest, so raise the limit or add a pooler.
  `db-connection-idle-in-transaction-count` above 0 with `db-transaction-oldest-age` climbing is a
  leaked transaction, a fault to find rather than capacity to buy.
- **The lag is not the server's.** `ingest-lag` high while the lanes are idle and the backlog near 0:
  samples arrive late (a spool replaying after an outage, a slow WAN) or the outpost's clock is
  behind. The lag is commit time minus the sample's timestamp, two clocks subtracted
  ([ADR-1628](/architecture/decisions/#adr-1628-ingest-lag-is-the-commit-time-minus-the-sample-ts-read-on-the-server)).
- **A tick is the ceiling.** `calc-pending-depth` growing while `calc-pass-duration` nears its
  interval, or `outbox-due-age` growing: that tick, not ingest, has fallen behind.

The seeded `ingest-lag-high` rule opens a warning alarm on the server's component when
`ingest-lag-max` holds over 30 seconds for 2 minutes.

## What a driver costs an outpost

An outpost's size is the sum of what its tasks cost it, and that differs by driver: parsing a large
JSON answer, walking an SNMP table and asking a held session a short question are different work. The
lab's [driver cost sweep](/developer/lab/#measuring-each-drivers-cost) measures each shipped driver
on an outpost with no simulator in its process, and `make gen` renders the result below
([ADR-1871](/architecture/decisions/#adr-1871-a-drivers-cost-is-a-slope-on-a-node-of-its-own-committed-and-rendered)).

- **By kind and interval.** The first table rolls drivers up by the transport they speak at a poll
  interval. A run costs what its kind costs whatever its interval, so **millicores per task** at an
  interval is the kind's **CPU per run** over that interval. Each figure is the median across the
  kind's measured drivers, with their range where more than one measured it.
- **Memory per endpoint** is what one endpoint on the driver holds on the outpost; for a session
  transport it is the held session.
- **To size an outpost**, add memory per endpoint over its endpoints and CPU per run over the interval
  over its tasks, beyond the idle outpost.
- **Per driver**, memory and millicores per task are slopes: what the outpost's container gains for
  each task it adds. **Warm memory** is paid once, when the first tasks of a driver land. **Thread CPU
  per run** is the outpost's own `poll-cpu-time`, and **thread share** its part of the container's
  figure: a low share is a transport doing its I/O elsewhere, not a cheap driver
  ([outposts](/architecture/self-monitoring/#self-monitoring-every-outposts-account-of-itself)).

The figures hold for the host and build named above the tables and for simulated devices, whose
answers are smaller and quicker than many real ones: read them as the relative cost of drivers and the
order of an outpost's footprint, not a promise for a site. A shipped driver the sweep has not
measured says why.

One limit on an outpost is not its cost: the server sends its worklist as one bus reply, and a reply
over the bus's maximum payload after compression (1 MiB by default) is refused, leaving the outpost on
its last worklist. That is about 18,000 tasks on one outpost; split a site's devices across outposts
well before it. Within a site, the server spreads unpinned components across its outposts by
expected cost
([load distribution](/architecture/outposts/#load-distribution-across-a-sites-outposts)).

## Platform configuration

Configuration comes in two tiers:

- **Bootstrap**, from the environment: what the process needs before the database exists, such as
  the Postgres DSN, the listen address, the encryption key and the ingest partitions. The
  [server variables reference](/deployment/container-image/#configuration) is generated from the
  code.
- **Everything else** is a [setting](/architecture/settings/): one typed declaration, resolved from
  the declared default, an optional settings file, the environment, and the admin's binding, with
  provenance on every key. Only the binding is stored.

## Horizontal scale and high availability

Today one server process owns the bus and the background loops: the Helm chart runs it with the
`Recreate` strategy so two never share the JetStream store. The outposts scale out freely, one or
many per site, and the edge rides out a WAN outage on its own spool. Postgres high availability is the
database's concern (a managed cluster, an operator).

:::design[More than one server, tracked in #2617]
Several servers run against one database and one bus: the API is stateless behind a load balancer,
the bus is a JetStream cluster, and each singleton (the background loops, the worklist and heartbeat
consumers) runs on one replica at a time and moves on failure, so the server tier has no single point
of failure. The clock's lease is #419.
:::

## Multi-tenancy: per database, per account, per deployment

Tenant isolation is physical, not a row predicate: a tenant is **one database and one deployment**.
There is no `tenant_id` column anywhere and nothing shared to reach across, so the data model stays
single-tenant in shape and multi-tenancy lives in orchestration.

:::design[A NATS account per tenant, tracked in #529]
Where tenants share a NATS cluster, each is one NATS account, so per-database isolation (storage) and
per-account isolation (the bus) are the same boundary.
:::
