A template is an **example configuration an operator clones**. It ships inside the binary as a menu,
never as data: nothing is inserted until somebody picks one, and what they pick lands as ordinary rows
they own outright. **Nothing points back at the template**: forking is one-time, no inheritance, no
back-pointer, so a template can be rewritten in any release without migrating a single install.

## Fork, not pin

This page used to describe the opposite model, **immutable versioned shapes that instances pin**,
retired by
[ADR-0071](/architecture/decisions/#adr-0071-a-template-is-a-clonable-example-not-a-versioned-shape-an-instance-pins).
The current model inverts it: a template is a starting point an instance copies and then forgets,
so **a template can change freely, because no instance is watching**. Same word, opposite purpose.

What replaced the pinned shapes is not a template at all:

| The shape of a... | is its... | and the relationship is |
|---|---|---|
| component | [`product`](/architecture/core-entities/), with its `product_property` contract, naming its [driver](/architecture/collection/#drivers-the-declarative-menu) | a pointer, `component.product_id` |
| system | [`standard`](/architecture/core-entities/) | **conformance**, with live inheritance |

**Forking applies template to row. Conformance applies row to instance.** Only the second is live:
a standard's contract default resolves for every conforming system until that system overrides it.
A template's link is severed at creation. How to reach and read a class of component is not a
template's job either: that is the driver's spec
([ADR-0827](/architecture/decisions/#adr-0827-the-template-layer-owns-the-clone-model-and-the-componenttemplate-authoring-model-is-superseded-by-the-driver-spec)).

## The four kinds

A template is one of four kinds, each naming what it creates:

- **A standard template**: a [standard](/architecture/core-entities/)'s attributes, its
  [system roles](/architecture/core-entities/#system-roles-the-slots-a-system-needs-filled) (accepted
  types, pinned products, quorum, capacity, choices), and its property and metric contract lines.
  Forking one scaffolds the contract and the roles in the same write, which answers what a template
  carries: everything the standard declares, so "start from a meeting room" yields the slots the
  space needs filled, not only a name.
- **A component template**: a product, a driver attach preset (every driver input except the address,
  secret inputs as references), and declared property values.
- **A system template**: a standard (a standard template by name, or an existing standard), a
  component template or a product per role, and declared system property values.
- **A place template**: a nested tree of places, each naming a location type, an optional label, and
  optional nested places and system templates.

A location type is not a template kind. Since
[ADR-0106](/architecture/decisions/#adr-0106-a-location-type-is-platform-owned-and-a-nullable-object-clears-under-the-mask)
a location type is an official row an operator reshapes through the
[registry fork](/architecture/decisions/#adr-0095-an-operator-forks-a-shipped-registry-row-instead-of-the-platform-writing-it),
so what places get is a template for a **subtree of places**, each place's type checked against its
parent's allowance, and no wording or logic keyed on any particular type.

## How a template ships

**Authored as kind-tagged YAML in the repo and `go:embed`ed into the binary** (an `internal/template`
package), exactly like the seed files; the difference is the loader. A **seed** inserts rows unasked; a
**template** inserts nothing. The loader exposes a read-only catalog, validated against the template
schema at load (an unknown field, a role naming half a choice, a system template leaving a role
unfilled or answering a choice two ways, a component preset setting the address are all refused,
naming the template), and never writes a row: a template addressable as a row, or inserted wholesale,
would become shipped data carrying every update-versus-local-edit problem the model exists to avoid.
A build test dry-runs every template against the seeded catalogs: each product, component and system
type, driver input, property, metric and location type a template names must exist there, and a
nested place's type must allow its parent's, so a template naming a row a release withdrew fails the
build, naming the template and the row, rather than an operator.

There is **no template versioning**: a template is addressed by its name and replaced by the next
release. Only shipped templates exist; an operator authoring or saving a template of their own is
[#1330](https://github.com/hyperscaleav/omniglass/issues/1330). The stand-in standards seed is retired:
a fresh install starts with no standards, and the catalog offers them.

## Reading a template

**`GET /templates`** (optionally one `kind`) and **`GET /templates/{template}`**, gated
`template:read`, which the viewer's `*:read` floor already grants. A catalog read is a registry read:
no owner and no scope injection. The body is the template whole: its kind and the body that kind
carries. The CLI is `omniglass template list` and `omniglass template get <template>`.

## Forking a standard

**`POST /standards:fork`** (`omniglass standard fork --template <template>`), gated `standard:create`,
writes one operator-owned standard (`official: false`) with the template's roles, choices, property
and metric contract lines and map, in one transaction, under a name the operator chooses (the
template's by default). A taken name is a 409. A variant forks only once the operator holds the
standard it hangs off (one they name, or theirs named for the template's parent), otherwise a 422
names the template to fork first: chains do not fork in one call. The fork is audited once, as `fork`,
with the template's name in its detail, which is the only trace of where the standard came from.
Editing it, renaming it, deleting it, and booting a release whose template changed all leave the other
untouched. The dev seed and the lab fork every standard template through the same primitive, so their
fleets have the standards their systems conform to.

## Instantiating from a template

Three custom methods start fleet entities from a template, each on the collection it creates in and
gated by that resource's own create permission. Each turns the template into one **plan** and lands it
through the planned-system primitive ([below](#one-primitive-lands-a-plan)): every piece is the
ordinary create, checked as its own route checks it, in the caller's own scope, with its own audit row,
in **one transaction**. A refused piece is answered as its own route answers it, and nothing lands.

- **`POST /components:instantiate`** (`component:create`): one component from a component template at
  a place, with its product and the template's declared values (which also need `component:update`).
  When the request's `inputs` carry the address (`host`) and a `node`, its endpoint attaches through the
  driver, the template's preset under the inputs given (which also needs `endpoint:create`). A secret
  input names a secret the caller may read, resolved exactly as an attach resolves it, so one the caller
  cannot use is refused indistinguishably from one that does not exist. Inputs with no address, or an
  address with no node, are a 422.
- **`POST /systems:instantiate`** (`system:create`, and `system:read`, `system:update`,
  `component:create`, `component:update`): a whole system from a system template at a place, built to
  the standard the caller names, else the template's own: the caller's standard of that name when they
  hold one, otherwise forked from its standard template in the same write, with every ancestor of a
  variant the fleet does not hold, parents first (which needs `standard:create`). A component is
  created for each role, filled to its quorum with the product the template names, and assigned, so the
  system's staffing reads complete. A role given an address in `attach` (one object per component of
  the role) lands attached; the rest land unattached and are listed in `to_attach`. A standard the
  template cannot staff (a fill whose product is not a type its role accepts, or a role it does not
  fill) is a 422 naming the roles.
- **`POST /locations:instantiate`** (`location:create`, and the system permissions above when the
  subtree carries systems): a subtree of places from a place template under a parent place, or as a new
  top. Each place's type must be one the fleet holds and must allow its parent's type, read from the
  fleet's own effective `allowed_parent_types` (an operator's fork of a shipped type included), and each
  is named by the template, the request (the root), or its type's name rule. The systems the template
  places land staffed and unattached. A type the fleet lacks is a 422 naming the type; a placement its
  types refuse is a 422 naming the pair. Nothing is keyed on any particular type.

A place outside the caller's location read scope is a non-disclosing 404, and an unknown template a
404. The CLI is `omniglass component instantiate`, `omniglass system instantiate` and
`omniglass location instantiate`.

**Provenance lives in the audit trail only**, as it does for a fork: every audit row a plan writes
carries the template's name as `instantiated_from`. No column and no back-pointer, which keeps the copy
severed while still answering "where did this come from"; removing a template from the catalog leaves
every row created from it reading identically.

## One primitive lands a plan

The simulator's "add a simulated system" and the three instantiations share one primitive in two
halves. The pure planner (`internal/systemplan`) staffs a standard's roles from each role's candidate
products: the products the simulator serves, or the one product a template names for the role. It
fills each role to its quorum (capped by its capacity) and takes one alternate per choice. The planned
create (`storage.CreatePlan`) then lands the standards to fork, the places parents first, each system
with its components, their endpoints, declared values and role assignments, and any standalone
components, in one transaction.

## Why this dissolves the shipped-defaults problem

The thing the vendor updates and the thing the operator owns are **never the same object**, so a
template change never needs a migration. Authoritative rows either overwrite operator edits or
freeze the defaults; pinned versions mean persuading every install to re-point. Forking has nothing
to reconcile.

:::design[Trust: the signature and the capability manifest, tracked in #318]
The trust surface of a catalog accepting templates from outside the binary (the hosted /
marketplace path), which matters only once templates arrive from somewhere other than the release:

- **template signature / attestation**: an optional author signature verified on import;
  authenticity, distinct from the content-hash integrity check. Verified on the hosted /
  marketplace path regardless of the self-host runtime stance.
- **capability manifest**: which write-commands and credential shapes a template exercises, shown
  and approved at fork time, so a device-mutating template never gains powers the operator did not
  see.
:::
