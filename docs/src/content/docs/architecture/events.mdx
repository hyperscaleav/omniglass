An **event** is our semantic assertion that something happened, in our vocabulary: a discrete,
point-in-time occurrence the action layer reacts to, owned through the same exclusive arc as a sample.
It is not a sample ([the has-a-value-now razor](/architecture/properties/#the-has-a-value-now-razor-sample-vs-event)):
samples are what rules read, and events are what event rules produce. To operate event types, see
[the admin Events page](/admin/events/). The model is
[ADR-0063](/architecture/decisions/#adr-0063-the-telemetry-model-is-typed-registries-over-bare-noun-data-tables).

## The event_type catalog

A sample and an event are different shapes, so each gets its own catalog: `metric_type` and
`property_type` for [samples](/architecture/properties/#the-two-catalogs), `event_type` for events.
An `event_type` row is `(name, label, payload_schema, official, ...)`. It is built: list, get and
custom-type create, update and delete over `/event-types`, with seeded official types
(`call-started`, `command-issued`) that are read-only and operator-extensible beside them. Declaring
types gives events a known schema and makes them inspectable.

:::caution[Open question]
Today `official` is a boolean. Whether the sample catalog's fuller org and official scope ladder
extends to event types is undecided.
:::

## Events: caught, caused, derived, scheduled

An event's **origin** is one of four, none manufactured from a value flip (a transition is already
two consecutive sample rows):

1. **caught**: a component publishes a structured occurrence natively (an xAPI event, a webhook, an
   SNMP trap), and a driver's emit maps it to its event type
   ([an emit lands on any lane](/architecture/collection/#an-emit-lands-on-any-lane)). Built: it is
   validated against `event_type` and landed under the same owner confinement and reject-not-project
   as a metric.
2. **caused**: we issued a [command](/architecture/commands/), recorded as a `command-issued` event.
   Built.
3. **derived**: an event rule fuses signals into an operator-meaningful fact. Built for event rules:
   a rule writes its fire event when it fires and its clear event when it clears, once per edge, in
   the same transaction as the alarm transition ([alarms and actions](/architecture/alarms-actions/#the-event_rule)).
4. **scheduled**: the clock fired a schedule.

:::design[Log derivation and the scheduled producer, tracked in #410 and #419]
Derivation rules that turn a raw log line into a registered event, and the clock that writes
`origin=scheduled` events (a leader-elected singleton), are not built.
:::

Raw log lines are a separate ingest lane, not events
([ADR-0066](/architecture/decisions/#adr-0066-logs-are-a-raw-ingest-lane-not-events)): the
component-only `log_line` table and the outpost-owned `outpost_log` self-log table
([ADR-0079](/architecture/decisions/#adr-0079-five-telemetry-lanes-and-property-stops-being-the-genus)).

## Storage

The `event` row is the semantic-occurrence log and `event_type` its key catalog. An event carries the
lineage columns that name what produced it (`source_event_id`, `source_log_line_id`,
`derived_by_rule_id`), a flat `correlation_id` that threads a causal chain, and a nullable `alarm_id`:
a rule's fire event names the alarm it opened and its clear event the alarm it resolved. The component
and system event reads return the rule and the alarm on each such row. Layout and partitioning live on
[storage](/architecture/storage/).

:::design[The CDC publisher for event consumers, tracked in #2611]
An event is born in a Postgres transaction on the record lane, and a change-data-capture publisher
would fan the committed row onto JetStream for the action consumers, with no dual write
([messaging](/architecture/messaging/)). The publisher is not built.
:::
