A **secret** is an encrypted-at-rest value (an SNMP community, a set of basic-auth
credentials): typed, owned at one scope, and resolved down the [cascade](/architecture/cascade/)
so the most-specific owner wins onto a component. Its plaintext sibling is a
[variable](/admin/variables/). The model underneath is [config and
credentials](/architecture/variables/).

## The directory

**Values > Secrets** (with `secret:read`) lists every secret you may see. Each row shows its name
under its **label** where it has one, a **type badge**, a **scope** label (Platform, or the location
or component it attaches to), and a **masked** field preview (`••••••`, never a value). The list
reads in label order, with the secrets that carry none at the end, and the same chip filter as the
fleet lists narrows it.

::screenshot{#secrets}

`secret` is a **sensitive resource**, off the `*:read` floor, so a plain read-everything **viewer**
does not see this page at all; an **operator** or **deploy** holds an explicit scoped `secret:read`
and sees the secrets in its subtree. The directory is **scope-filtered** (you see your subtree, not
the whole fleet) and **hides admin-sensitive secrets** (platform credentials) from anyone below
admin, so their existence and field names never appear to an operator.

## Secret types

Every secret takes a **type**: a shape declaring the **fields** a secret of it expects, each with a
scalar type and whether the field is itself secret (masked and encrypted). The type is what the
create drawer renders as inputs. The shipped set, rendered from the seed itself:

<SeededSet kind="secret_types" />

The types are **authoritative reference data**, upserted on every boot, so a release can correct a
shape and the correction lands everywhere. They are **read-only for everyone**: there is no create
route, and their page (`/secret-types`, reached by URL, with no subrail entry) shows each type's
fields in a detail blade with Edit and Delete greyed, "Official: ships with Omniglass and updates
with it." The gate is `secret:read`, the same as the directory: whoever may read secrets may read
the shapes they take, and nobody else. See [the seed
model](/architecture/core-entities/#the-seed-model-templates-versus-canonical-catalogs).

Each type also carries a **sensitivity default**: an integration type like `oauth2-client` mints an
**admin-sensitive** secret (admin and owner only), a device type an operational one.

## Create

**New secret** (with `secret:create`) opens a create drawer:

- a **name**: lowercase letters, digits, and hyphens, no dots and no underscores, unique per owner;
  the cascade resolves by it;
- a **type**, from the set above;
- a **scope** (platform, location, or component; a secret has no system band, ADR-0052), then the
  entity itself from the shared tree picker;
- the type's fields, with a password input for each secret field.

A **platform** secret is install-wide, so it needs an all-scope grant plus `platform:create` on top
of `secret:create`; without it the **Platform** scope is not offered, and the form says which
capability that takes. Creating an admin-sensitive secret requires the **admin tier**, so an
operator can mint only operational secrets.

## Reveal, bind, and rotate

Pick a row to open its **detail blade**. Fields render masked.

- **Reveal secret values** (with `secret:reveal`) runs the audited decrypt and shows the plaintext
  with a per-field **Copy**. An operator reveals the operational secrets in its scope; an
  admin-sensitive secret is admin and owner only (anyone below admin gets a non-disclosing not-found).
  Every reveal is written to the [audit trail](/admin/audit/).
- **Binding** a secret (naming it as an endpoint input, a notification target's signing secret, or
  the mail relay's login) is its own permission, **`secret:bind`**, separate from reveal: it decides
  who may choose where a credential is sent, not who may read it. A role can bind without revealing,
  which is what an [agent](/guides/agents/) holds, since an agent never reveals.
- The footer **Edit** pencil (with `secret:update`) opens inline field edit; a **blank** secret field
  keeps its stored value, so you rotate one field without re-entering the rest. **Delete** (with
  `secret:delete`, admin and owner) sits behind a confirm. On a **Platform** row both also need the
  matching `platform:<action>`; holding only the secret half leaves the blade read-only with a note
  naming what is missing.

## From the CLI

`omniglass secret list` / `create` / `update` / `reveal` / `copy` / `delete`, and
`omniglass secret-type list` for the types (see the [CLI reference](/reference/cli/)). Each takes the
secret by name: `omniglass secret update demo-panel-login --fields '{"password":"rotated"}'`. A name
sealed at more than one owner you can see (a room shadowing the platform's) is refused with each
spelling that resolves, the owner first: `omniglass secret reveal '$platform/demo-panel-login'`, or
`boi.17c/demo-panel-login` for the room's.
